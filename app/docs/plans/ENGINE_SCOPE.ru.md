# Новая версия: llama.cpp и Strata

Дата: 2026-10-22. Статус: E0–E3 реализованы в рабочем коде; автоматические проверки и Windows-проверка миграции/llama.cpp пройдены. Полный E4 для реального инференса Strata остаётся ограничен отсутствием весов. Ход работы и границы владения: [журнал реализации](IMPLEMENTATION-COORDINATION.ru.md), [отчёт приёмки](IMPLEMENTATION-ACCEPTANCE.ru.md).

## Целевая граница

Поддерживаемые локальные движки: `llama_cpp` и `strata`. Удалить активную поддержку Ollama, QwFNfer и Infernix из интерфейса, запуска, IPC, установки компонентов и релизной документации.

Это изменение касается движков инференса. Агенты, чат и внешние API-подключения имеют отдельный жизненный цикл; их удаление в этот план не входит. Общие функции HTTP и OpenAI-совместимых подключений сохраняются по назначению.

Скачивание моделей строится вокруг файлов из Hugging Face, общего каталога и проверок двух движков: [обновлённый план](MODEL_DOWNLOADS.ru.md). Ollama pull не входит в новую архитектуру. Один совместимый GGUF может использоваться обоими движками без обязательной второй копии.

## Почему удалять по слоям

В текущем `ServerEngine` перечислены пять движков. Их ветки встречаются в настройках, профилях, `EngineModel`, конфигураторах, метриках, бенчмарках, `RunManager`, адаптерах запуска, IPC-командах и установщике. Простое удаление кнопок сохраняет эту стоимость сопровождения.

Есть общие зависимости, которые нельзя удалить вместе с интеграцией: например, `engine_adapters.rs` и `runs.rs` используют `ollama::endpoint` для разбора серверных адресов. Сначала вынести необходимую валидацию в нейтральный модуль и покрыть её проверками, затем удалить модуль Ollama.

## Порядок работ

| Этап | Изменение | Критерий готовности |
| --- | --- | --- |
| E0. Правила обновления | Инвентаризация точек входа, резервная копия БД, политика старых профилей, общий реестр поддерживаемых движков | Определены поддерживаемые ID и поведение каждого старого формата |
| E1. Миграция состояния | Отделить активные настройки и запускаемые профили от сохранённых legacy-данных; вынести общие HTTP helpers | Старые данные читаются без аварии, удалённые engine ID нельзя запустить или неявно заменить другим движком |
| E2. Интерфейс и ядро | Удалить конфигураторы, фильтры, сервисы, adapter/runtime/benchmark/process-ветки и IPC трёх движков | В runtime-сборке работают только llama.cpp и Strata; отсутствуют фоновые обращения к удалённым сервисам |
| E3. Поставка и документация | Обновить manifest компонентов, PowerShell/NSIS и UI установщика, maintenance, setup, RU/EN, справку и notices | Чистая установка предлагает два движка; обновление не требует удалённых компонентов |
| E4. Регрессия | Проверить оба движка, роутер llama.cpp, Strata-конфигурации, профили, чат, агенты и обновление | Все обязательные сценарии проходят на Windows; готова основа для загрузчика |

Проводить небольшими проверяемыми изменениями: сначала E0/E1, затем вертикальное удаление интеграций с синхронной чисткой типов и IPC, затем поставка и приёмка. Не выпускать промежуточную сборку с недоступными миграциями или оставшимися кнопками запуска.

## Старые данные и модели

- Перед миграцией сделать резервную копию БД существующим механизмом. Миграция должна быть транзакционной и повторно безопасной.
- Сохранить исходные профили и legacy-поля для экспорта и объяснения пользователю. Для неподдерживаемых профилей предусмотреть явный статус и экспорт; исключить их из автозапуска, роутинга, бенчмарков и активного выбора.
- В текущем v2 `engine` уже хранится строкой: использовать это для безопасного чтения старых записей. Тип запуска может содержать только два поддерживаемых значения; импорт и восстановление проверяют ID до применения настроек.
- Если ранее был выбран удалённый движок, открыть выбор llama.cpp/Strata и сообщить причину. Не трактовать неизвестный ID как llama.cpp и не переносить несовместимые параметры автоматически.
- Автозапуск при таком обновлении отключить до выбора валидного профиля. Восстановление last-known-good также должно соблюдать новую границу запуска.
- Установленные движки, внешние службы, Ollama blobs и веса пользователя не удалять обновлением. Управление устаревшими installer-owned компонентами при необходимости оставить только в узком механизме обслуживания, без поддержки запуска.
- Существующие GGUF могут обнаруживаться как обычные файлы и использоваться llama.cpp/Strata после проверки. Не переименовывать и не извлекать blobs автоматически.
- Общие файлы и ссылки из сохранённых профилей учитывать при обслуживании. Сохранение legacy-данных не требует сетевых запросов к старым движкам или их присутствия в активном каталоге.

## Карта изменений

- Frontend: `src/types/app.ts`, `src/types/config.ts`, `src/types/runtime.ts`, `src/lib/engineModels.ts`, `src/store/control.ts`, `src/features/profiles/`, `src/features/launches/`, конфигураторы, библиотека, настройки, setup, demo и переводы.
- Rust: `src-tauri/src/lib.rs`, `engine_adapters.rs`, `runs.rs`, `process.rs`, `runtime.rs`, `benchmark.rs`, `engine_integration.rs`, `settings.rs`, `app_lifecycle.rs`, профили, recovery, миграции, артефакты и удаляемые engine-модули.
- Поставка: `src-tauri/installer/components.json`, `Install-Components.ps1`, `components.nsh`, `installer.nsi`, installer UI и связанные скрипты; `components.rs`, `component_maintenance.rs`, release scripts и CI-проверки.
- Контракты: ошибки старого engine ID должны быть одинаково понятны в UI и Rust; неизвестные значения не проходят в default-ветку запуска.
- Документация и лицензии: README RU/EN, таблица движков, API-справка, IPC, changelog и third-party notices. Уведомления удалять по фактическому составу поставки; исторические отчёты и записи миграций могут сохранять имена старых движков.

## Обязательная приёмка

1. Чистая установка: доступны только llama.cpp и Strata, установщик и настройки согласованы.
2. Обновление реальной копии БД с каждым из трёх старых выбранных движков, профилями, секретами и recovery-снимками: запуск приложения успешен, данные доступны для экспорта, автоматического запуска нет.
3. Импорт неподдерживаемого профиля, старые IPC-команды и попытка восстановить legacy-профиль: понятный отказ без частичного применения настроек или подмены движка.
4. llama.cpp: single model, start/stop/restart, профили, native router, метрики, бенчмарк и подбор параметров.
5. Strata: обнаружение подготовленных конфигураций, запуск, остановка, restart, метрики и предусмотренные текущей интеграцией тесты.
6. Чат и агенты продолжают обращаться к серверам обоих движков; внешние API-подключения работают через свои общие механизмы.
7. Библиотека не создаёт копии весов и не предлагает удалённые движки; общие GGUF и проекторы определяются корректно.
8. Полный выход, трей и обслуживание не обращаются к старым сервисам и не удаляют внешние установки или модели.
9. Проверки frontend/Rust, source/docs/module verification, installer checks и ручные сценарии Windows проходят. Поиск имён старых движков допускает только обоснованные migration/legacy/history-упоминания.

## Оценка и последовательность релиза

Предварительно **4–7 рабочих дней** на удаление интеграций с миграцией и проверками одного разработчика; уточнить после E0. Это отдельная работа и она не входит в оценку загрузчика.

Рекомендуемая последовательность новой версии: E0–E4 → первая загрузка GGUF из Hugging Face → шарды и восстановление → приёмка установки моделей. План загрузчика оценивает эту часть ещё в 9–14 рабочих дней. Оценки не включают автоматический мастер подготовки Strata или полноценный каталог поиска.

Версию и дату выпуска назначить после приёмки. Решение об удалении поддержки отразить в changelog и заметном сообщении при первом обновлении.
