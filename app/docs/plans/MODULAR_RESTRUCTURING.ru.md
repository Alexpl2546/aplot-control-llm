## 1. Согласованная цель и границы

**Одно настольное приложение с текущим UI управляет несколькими локальными движками, моделями и профилями; помогает подобрать конфигурации под оборудование и подключить их к внешнему harness.**

Обязательные свойства:

1. Один экземпляр Aplot, одно главное окно, общие настройки, каталог и история. Фоновые процессы движков управляются внутри этого приложения.
2. Несколько одновременных запусков: одинаковые или разные движки, модели и профили, если это допускают движки и ресурсы.
3. Сохранение текущего оформления, навигации, карточек, раскладки dashboard, тем, масштабирования, RU/EN и привычных сценариев.
4. Сохранение возможностей пяти текущих движков: llama.cpp, Strata, Ollama, QwFNfer, Infernix. Новая архитектура не обещает одинаковые возможности у всех.
5. Полноценные профили для каждого движка, независимые от глобального выбора в интерфейсе.
6. Подбор модели и настроек, оценка ресурсов, реальные измерения и история сравнения.
7. Подключение к внешнему harness: автоматически для проверенных адаптеров, полуавтоматически или копированием API для остальных.
8. Понятные модули и подробная синхронизированная документация на русском и английском.

В эту работу не входят собственный агентный цикл, инструменты агента, память диалогов, редактор workflow, встроенный агентный чат, распределённый кластер и маркетплейс внешних плагинов. Также не планируются смена технологического стека и общий редизайн.

Идею расширяемости реализуем внутренними модулями с контрактами. Внешний plugin API можно обсуждать после проверки контрактов реальными интеграциями.

- [Предложение встроить агента](../AGENT_INTEGRATION.md): встроенный чат/RPC/инструменты не относятся к этому плану. Исторический документ не удалять; при реализации поставить отметку о смене направления и ссылку на новое решение.

## 3. Предметная модель

| Сущность | Назначение и жизненный цикл |
| --- | --- |
| `EngineInstallation` | Конкретная установка/сборка движка: пути, версия, обнаруженные возможности. Один адаптер может обслуживать несколько установок |
| `ModelArtifact` | Комплект файлов модели, шардов и зависимостей; источник, размеры, идентичность, проверка целостности |
| `LaunchProfile` | Сохранённая конфигурация с устойчивым ID, ревизией, ссылками на модель/установку и параметрами движка |
| `LaunchPlan` | Проверенный план исполнения: команда, окружение, рабочая папка, адреса, ресурсы, ограничения. Создаётся до запуска |
| `EngineService` | Собственный фоновый процесс либо подключённый внешний сервис; один сервис может обслуживать несколько моделей |
| `ModelDeployment` | Доступная через сервис модель или маршрут; размещение/выгрузка отличаются от остановки сервиса |
| `RunSession` | Управляемый пользователем запуск по снимку профиля, связанный с сервисом и deployment. Имеет runId, generation и состояние |
| `ConnectionTarget` | Адрес, протокол, действующий ID модели, настроенный контекст и ссылка на секрет для внешнего клиента |
| `HarnessConnection` | Какой harness, какой адаптер/версия, какое подключение, какие изменения применены и что проверено |
| `BenchmarkJob` / `BenchmarkResult` | Изолированное задание измерения и сохранённые условия/результаты |
| `ResourceLease` | Временное резервирование доступных ресурсов для запуска или проверки |

Важно различать:

- Профиль — данные; сохранение профиля не запускает процесс.
- Запуск использует неизменяемый снимок ревизии профиля. Изменение черновика не меняет работающий сервер.
- В обычном single-model режиме сервис и deployment практически соответствуют одному запуску. Ollama и нативный роутер требуют связей один-ко-многим.
- Сервис может находиться в ready, пока конкретная модель загружается или выгружена. Эти состояния нельзя склеивать.
- Один файл весов может использоваться несколькими профилями и движками. Совместное хранение файла не гарантирует совместное использование RAM/VRAM процессами.
- Два профиля Ollama одной модели с разными параметрами не считаются независимыми размещениями без подтверждения возможностей сервиса; адаптер сообщает конфликт либо поддерживаемый режим.

Связи: профиль → план → запуск; запуск → сервис + deployment; подключение → deployment или API-алиас; тест → снимок запуска/плана + аренда ресурсов. История сохраняет снимки даже после изменения или удаления профиля.

Сохраняем React/TypeScript/Zustand, Tauri/Rust и SQLite. Rust отвечает за процессы, проверку исполняемых планов и постоянные данные. TypeScript отвечает за представление и черновики; значения в UI повторно проверяются на backend.

Целевая раскладка, без обязательного создания всех папок сразу:

```text

    planner/ benchmarks/ connections/

  store/                        доменные slices и временный control-фасад
```

Направления зависимостей проверяются в CI. `shared` не становится местом для всей логики; новые абстракции вводятся при наличии реального общего поведения. Один Rust crate первоначально достаточен.

## 5. Контракты и настройки

### 5.1 Адаптер движка

Минимальные операции: `discover`, `capabilities`, `validateProfile`, `prepareLaunch`, `health`, `listDeployments`, `runtime`. Управление resident-моделями, подсчёт токенов и специальные API — дополнительные возможности, а не обязательные заглушки.

`prepareLaunch` возвращает план; общий supervisor выполняет process lifecycle. Версия/сборка входит в ключ обнаруженных возможностей. Значения capability: supported / unsupported / unknown с основанием и условиями. Функции вроде tool calls проверяются для сочетания движок + модель + шаблон, а не только для бинарника.

Первый адаптер оборачивает текущую реализацию llama.cpp; затем переносим Strata, QwFNfer, Infernix и особый service/deployment путь Ollama. Реальную совместимость устанавливаем проверками, не переводом всех флагов llama.cpp.

### 5.2 Профиль v2 и разрешение значений

Оболочка: `schemaVersion`, `id`, `revision`, `name`, `engineInstallationId`, `modelArtifactId`, `mode`, `engineOptions`, `connectionOptions`, `requestDefaults`. `engineOptions` — типизированное объединение по движку с сохранением всех специфических параметров. Опции router принадлежат конфигурации сервиса и набору маршрутов.

Порядок: defaults конкретной установки → сохранённый профиль → явные изменения запуска. Пресет — применение набора значений к профилю, первоначально без цепочки наследования. Итоговый snapshot содержит значения и их происхождение. У `auto` сохраняются запрошенное значение и фактически обнаруженный результат, если движок его сообщает.

Параметры запуска отделяются от defaults HTTP-запросов. Defaults, которые не поддерживаются движком или клиентом, нельзя объявлять применёнными.

Описание параметра содержит тип, единицы, значение по умолчанию, диапазон, условие доступности, зависимости, область изменения и RU/EN пояснения. Существующий `PARAMETER_REGISTRY` используется при переходе. Проверяемые схемы и IPC-типы имеют назначенный источник истины; генерация исключает две вручную поддерживаемые конкурирующие схемы. Особые формы сохраняют существующие компоненты и стиль.

Неизвестные поля импортированного профиля сохраняются для диагностики/повторного экспорта, но не исполняются автоматически. Более новая неподдерживаемая версия получает явный статус. `extraArgs` остаётся для совместимости там, где уже поддерживается, с проверкой конфликтов управляемых флагов.

### 5.3 IPC и события

Команды: `prepare_run`, `start_run`, `stop_run`, `restart_run`, `list_runs`, `run_snapshot`, `list_engine_installations`, `resolve_profile`, `preview_connection`, `apply_connection`, `revert_connection`, `start_benchmark`, `cancel_job`. Имена предварительные.

Каждая изменяющая операция имеет operationId и целевой runId/serviceId; повторная доставка не создаёт случайный второй процесс. Событие содержит schemaVersion, eventId, timestamp, correlationId, runId/serviceId/deploymentId при применимости, generation и payload. Поздний результат предыдущего поколения игнорируется именно для своего запуска.

Ошибки имеют code, messageKey, details и retryability. Не смешиваем занятый порт, несовместимую модель, нехватку памяти, ошибку сборки и недоступное подключение. Старые команды остаются временным фасадом к выбранному запуску до перевода UI; затем удаляются после проверки всех callers.

### 5.4 Хранение и идентичность

Вводим последовательные schema migrations с журналом, транзакциями и согласованным backup SQLite. Предлагаемые записи: установки, artifacts/file references, профили v2, run history, connection records, jobs/results, migrations. Не сохраняем `Child` или PID как достаточное доказательство владения после перезапуска.

Миграция сохраняет ID старых профилей, порядок/имена, избранное, раскладку, язык, темы, settings, историю тестов и recovery. Глобальные настройки Strata/QwFNfer/Infernix преобразуются в отдельные профили; подготовленные Strata-конфиги остаются файлами-источниками, которые не переписываются без действия пользователя. Неоднозначные записи помечаются для уточнения без потери оригинала.

Профиль v1 и raw legacy JSON импортируются; экспорт v2 явно версионируется. Экспорт в старый формат разрешён только для представимого подмножества с объяснением потерь. Исторические тесты не получают выдуманных версий движка или fingerprints.

Секреты отделяются от публичной конфигурации через secret reference и исключаются из fingerprint/логов/экспорта по умолчанию. Способ Windows-хранения выбирается в D06 с учётом переносимой установки; миграция не должна потерять действующие ключи.

## 6. Жизненный цикл и несколько моделей

Supervisor содержит реестр сервисов и запусков, индивидуальные блокировки операций и короткую общую блокировку регистрации/резервирования. Ожидание HTTP или завершения процесса не удерживает общий lock.

Сохраняем знакомые состояния stopped / starting / loading / ready / busy / stopping / restarting / crashed, но отдельно для сервиса и deployment. Операция проверки может дополнительно быть queued / cancelled / restoring / failed; это не состояние всех серверов.

Правила:

1. Старт B не останавливает A. Остановка/рестарт B не меняет снимки и логи A.
2. Порты резервируются централизованно до spawn. Проверка bind не исключает внешнюю гонку; ошибка фактического запуска снимает резерв и сообщает причину.
3. Операции одного запуска упорядочены; crash одного движка не завершает приложение и остальные процессы.
4. Штатное завершение Aplot останавливает принадлежащие ему процессы с ограниченным ожиданием. Сворачивание/закрытие в трей сохраняет запуски. Отдельный постоянный daemon первоначально не вводится.
5. Внешний сервис не останавливается и не уничтожается как собственный. Статус managed/external явно виден; изменяющие действия над его моделями отделены от наблюдения.
6. Общий Ollama service имеет нескольких потребителей; остановка одного deployment не убивает сервис остальных. Проверяются конфликты контекста и модели.
7. Нативный router llama.cpp — один сервис с набором маршрутов. Первый перенос воспроизводит нынешний набор профилей; далее изменения применяются только к router, который использует эти профили. Recovery восстанавливает согласованный набор этого router, а не чужие новые профили.
8. Recovery хранит рабочий снимок на запуск/набор маршрутов. Неуспешный кандидат не уничтожает рабочую редакцию.
9. При новом старте приложения оставшиеся записи запусков проверяются; живой процесс не считается собственным по совпадению PID. Автовосстановление списка запусков — явно настроенное поведение, первоначально выключенное.

Hardware собирается один раз за интервал, engine runtime — отдельно по сервисам; общие сервисы не опрашиваются повторно для каждого профиля. Ограничиваем параллельность, частоту, историю логов и графиков; ошибка одного endpoint не тормозит все опросы.

Резервирование памяти учитывает текущие наблюдения и существующие leases без двойного вычитания уже размещённой памяти. Предварительная оценка не гарантирует allocation; учитываем пики загрузки, KV, workspace, pinned RAM, expert cache и SSD I/O. Универсальная точная формула для всех архитектур не обещается.

Общие действия вроде «Остановить все» выделены отдельно. Трей показывает общий статус и однозначную цель действий.

Раскладка dashboard сохраняется. История инференса принадлежит запуску; общая аппаратная история не дублируется. Для сводной скорости нельзя складывать несопоставимые показатели различных движков без определения метрики.

## 8. Каталог моделей, подбор и тестирование

### 8.1 Модели

Сохраняем текущий корень `models/`; рефакторинг не переносит автоматически существующие веса. Регистрируем комплекты файлов и зависимости: primary/shards, tokenizer, mmproj, LoRA, MTP/draft, n-gram, prepared config, Ollama blobs/manifests. Общие файлы и hardlinks считаются отдельно от логического размера модели.

ID каталога не должен терять избранное при изменении пути или давать ложную дедупликацию разных квантовок. Используем известный digest/checksum, иначе идентичность с явным уровнем уверенности. Полный hash десятков гигабайт не вычисляется при каждом открытии экрана.

Перед удалением показываем зависимости и активные запуски. Не удаляем используемый комплект без остановки его потребителей; учитываем другие модели, ссылающиеся на общие файлы. Освобождаемое физическое место оценивается с учётом hardlinks либо честно обозначается неизвестным. Недостающий файл становится состоянием missing, а не исчезновением всех связанных профилей.

Загрузки и импорт — отменяемые задания с staging, проверкой целостности и завершённой регистрацией. Сохранить текущие Ollama pull/import и локальный импорт; общую загрузку иных форматов добавлять отдельными адаптерами по мере потребности. Метаданные лицензии/источника сохраняются при наличии, не придумываются.

### 8.2 Подбор

Три уровня доказательств: оценка → проверенный запуск → измеренный сценарий/контекст. Минимальный контекст — жёсткое требование пользователя. Цели speed / context / balanced ранжируют только допустимые кандидаты; качество кода/рассуждений не определяется битностью или recall.

Первый завершённый подбор — llama.cpp на локальном оборудовании; затем собственные стратегии Strata и Infernix, далее QwFNfer/Ollama в пределах доступных knobs. Все движки остаются доступны вручную с первого этапа миграции. Не выдаём общий estimator llama.cpp за проверенную оценку MoE и pinned-memory allocation.

Учитываем совместное размещение: рекомендация «подходит отдельно» отличается от «подходит вместе с текущими запусками». Временно занятая память отличается от постоянной несовместимости. Trial не изменяет профили, recovery, router и настройки; использует отдельный runId и purpose.

### 8.3 Проверки и измерения

BenchmarkJob имеет cancel token, бюджет времени/кандидатов, resource lease и correlationId. Задание по общему GPU/сервису первоначально последовательное. Автоматическая остановка чужого запуска запрещена; для проверки с освобождением ресурсов показывается план и сохраняются исходные снимки.

Отмена прерывает запрос/ожидание и освобождает свои процессы/leases. Восстановление затронутого запуска имеет собственный outcome. Успешная отмена не маскирует ошибку восстановления.

Сохраняем throughput, exact recall, continuity и историю. В результат записываем идентичность модели/бинарника, параметры, оборудование/драйвер при наличии, доступные ресурсы, фоновые активные запуски, версию методики, seed, фактические токены, reserve ответа, raw evidence и missing metrics. Cold/warm prefix, запуск процесса и состояние файлового кеша обозначаются отдельно; не объявляем ОС-кеш сброшенным без фактического сброса.

Полноценные сравнительные измерения выполняются последовательно в сопоставимых условиях. Для выбора близких результатов задаём повторы и порядок кандидатов в протоколе. Старые измерения остаются историческими; новые условия не приписываются старому результату.

## 9. Подключение к внешним harness

Основной сценарий: выбрать готовый запуск → «Подключить» в текущем API-разделе/шапке → выбрать harness → проверить параметры → применить → увидеть результат. Пользователь не вводит повторно данные, уже известные Aplot.

| Режим | Результат |
| --- | --- |
| Автоматический | Адаптер использует поддерживаемый API/CLI/config механизмы конкретной версии; предварительный diff, backup, проверка, undo |
| Полуавтоматический | Готовый файл/фрагмент/команда с указанием места применения и оставшегося действия |
| Ручной | Копирование base URL, точного model ID, способа авторизации и действующего контекста отдельно либо блоком |

Контракт адаптера: обнаружить установку/версию, прочитать релевантную конфигурацию, проверить совместимость, сформировать preview, применить, проверить, отменить собственные изменения. При изменившемся после preview файле пересчитать diff; undo не затирает последующие чужие правки. Для нескольких файлов нужен журнал операции и компенсирующий rollback, а не обещание общей файловой транзакции.

Сохраняем пользовательские providers, модели, comments и неизвестные поля насколько это допускает формат. Повторное добавление того же подключения идемпотентно. Harness остаётся самостоятельной программой; автоматический запуск его агентных задач не входит в подключение.

ConnectionTarget берётся из фактического запуска/API, а не выбранного черновика. Используем действующий model ID, адрес с корректным suffix, актуальную авторизацию и настроенный контекст, а не максимальное значение из model card.

Статусы проверки раздельны: конфигурация подготовлена / записана / endpoint отвечает / модель отвечает / проверено из harness. Проверка Aplot не считается доказательством доступности из WSL, контейнера или другой машины. Для разных сетевых окружений нужны отдельные адреса и проверки.

Первый автоматический адаптер выбираем вместе с пользователем. До реализации изучаем официальные документы и реальную конфигурацию выбранной версии; названия/поддержка harness сейчас не закреплены. Следующий адаптер проверит, что контракт расширяется без изменения core.

Необязательный локальный gateway обсуждается после первого прямого подключения. Он даёт устойчивый адрес и aliases, но требует корректного streaming, cancellation, auth и model discovery. Сначала прозрачный проход одного выбранного протокола, обычно OpenAI Chat Completions; Responses/Anthropic не заявляются без реализации и проверки. Неподдерживаемые запросы отвергаются явно, не преобразуются молча. Смена alias не меняет уже выполняющийся запрос; остановленный target получает понятную ошибку. On-demand loading/fallback — отдельные будущие политики.

## 11. Этапы реализации

Ниже сохранены целевые критерии этапов; их наличие не означает завершения. Фактические результаты и непроверенные пункты перечислены в [прогрессе](IMPLEMENTATION_STATUS.ru.md). Размер S/M/L/XL — относительная сложность, не обещание сроков. После этапа получаем проверяемую рабочую редакцию.

### P00 — Базовая редакция, аудит и критерии сохранения UI [M]

**Задачи:** зафиксировать рабочее дерево вместе с текущими изменениями; составить актуальную карту зависимостей/сценариев; инвентаризировать поля settings/profiles и пути side effects; проверить команды сборки/тестов; снять контрольные состояния существующего UI. Использовать копию базы и изолированный корень, не менять рабочую установку тестами.

**Результат:** отчёт baseline, список известных дефектов, карта переноса файлов, визуальный эталон и первые ADR. Согласовать D01–D03, а также первую внешнюю интеграцию D04.

**Приёмка:** нынешний запуск каждого доступного движка и основные действия UI имеют описанный сценарий; известные сбои не скрыты. Проверены профиль/import/export/recovery, router/Ollama, раскладка, tray и singleton. Отсутствующий движок или модель помечены unavailable, не passed.

**Откат:** сохраняется исходная сборка и согласованный backup. Документация: overview, actual code map, baseline checks.

### P01 — Доменные контракты и совместимый фасад [M]

**Задачи:** ввести сущности раздела 3, ID, snapshots, capability/error/event типы и интерфейсы репозиториев. Определить версии IPC и профильного формата. Существующие действия направить через фасад без изменения поведения одного запуска.

**Результат:** domain-модули, typed bridge, чертёж dependencies и тестовые fixtures.

**Приёмка:** обычный запуск, метрики и профиль выполняются прежним способом; domain не импортирует React/Tauri/SQL. Целевые контракты проходят сериализацию Rust↔TS; нет потери полей специфических движков.

**Откат:** убрать новое использование фасада, сохранив legacy путь; база ещё не перестраивается. Документация: сущности, контракты, путь команды.

### P02 — Профили всех движков и миграции хранения [L]

**Задачи:** migrations, профиль v2, разрешение defaults/overrides, ревизии, secret references, совместимый импорт. Сохранить старые profiles и преобразовать global engine settings в полноценные профили. Вводить artifact references через legacy path references до завершения P06.

**Результат:** каждый текущий движок имеет несколько независимых сохраняемых профилей; настройка одного не переписывает остальные. Выбрать D06 и мигрировать ключи без потери доступа.

**Приёмка:** миграция на копии реальных данных сохраняет IDs, значения, избранное, layout, историю и recovery; повторный запуск migrations идемпотентен; сбой откатывает транзакцию. Импорт v1/raw и round-trip v2 проверены; missing paths не уничтожают запись.

**Откат:** закрыть новую редакцию и восстановить полный согласованный backup с прежним EXE. Старый EXE не должен открывать несовместимую новую схему. Документация: полная схема и инструкция возврата.

### P03 — Адаптеры пяти движков, первоначально один запуск [L]

**Задачи:** извлечь подготовку, validation, capabilities и runtime mapping из текущих ветвлений. Оборачивать существующий рабочий код по одному движку, не переписывать native kernels. Определить service/deployment semantics Ollama и router.

**Результат:** общий сценарий запуска с явным engine adapter; реестры настроек и возможностей сохраняют текущие controls.

**Приёмка:** CLI/config/request поведение сопоставлено с baseline; библиотека не отправляет native artifact неподходящему движку; unsupported/unknown различимы. Smoke на доступных установках, тесты mappings/auth/error handling, special native-router и Ollama paths.

**Откат:** переключить конкретный адаптер на legacy implementation. Документация: пять engine manuals и рецепт нового адаптера.

### P04 — Backend supervisor нескольких сервисов и запусков [XL]

**Задачи:** заменить одиночный current реестром; scoped generations, операции, владение, ports, event routing и shutdown. Добавить run listing/history и индивидуальный recovery. Реализовать shared services и reference tracking для Ollama/router.

**Результат:** backend независимо запускает, наблюдает, останавливает и перезапускает несколько целей; старый UI временно управляет выбранной через фасад.

**Приёмка:** A+B работают; stop/restart/crash B не меняет A; один занятый порт не ломает остальные; поздний event B не попадает в A; повторный Start не дублирует процесс. Quit останавливает own services, внешний сервис остаётся. Все race tests выполняются и на lightweight fixtures без больших весов.

**Откат:** временно ограничить новый manager одним запуском после штатной остановки остальных; вернуть P03, при изменении схемы — backup. Документация: locks, state machines, generations, ownership.

### P05 — Несколько запусков в существующем UI [L]

**Задачи:** domain slices и selectors; убрать глобальное смешение runtime/log/history; подключить выбор запуска в существующей шапке, фильтры и адреса. Перенести polling/subscriptions из App в сервис. Уточнить tray и действия restart/recovery.

**Результат:** одно окно управляет несколькими запусками в текущем стиле; смена выбранной карточки не влияет на работу серверов.

**Приёмка:** визуальное сравнение с P00; RU/EN, обе темы, текущая раскладка, длинные названия, keyboard, 1100×720/1500×900 и Windows scale 100/150/200%. Незавершённые черновики сохраняются при переключении; выбранный runtime не подтягивает настройки чужого запуска. Действия имеют однозначную цель.

**Откат:** вернуть UI фасада одного выбранного запуска; данные остальных не удаляются. Документация: обновлённые пути UI→backend, руководство запусков.

### P06 — Комплекты моделей и зависимости [L]

**Задачи:** artifact manifest/index поверх нынешних папок, shared files, digest/confidence, missing states, file dependencies; привязать профили к artifacts без смены существующих весов. Сохранить импорт/pull, описать отмену/staging/целостность.

**Результат:** пользователь понимает местоположение, использование и состав модели; профили перестают зависеть только от одного произвольного пути.

**Приёмка:** primary/shards/MTP/ngram/mmproj не смешиваются; избранное и legacy paths мигрируют; shared n-gram и hardlinks не считаются двумя физическими копиями. Preview удаления показывает все потребители; активные файлы не удаляются. На тестовых каталогах проверяются неполный комплект, отменённый импорт и общий файл.

**Откат:** индекс перестраивается из прежних каталогов; рефакторинг не требует отката перемещения весов. Документация: расположение, manifest, проверка и удаление.

### P07 — Общий учёт ресурсов и подбор [L]

**Задачи:** hardware service, resource leases, staging пиков, admission с объяснениями; адаптировать имеющийся hardware planner. Общий pipeline сначала для llama.cpp, затем измеряемые стратегии Strata/Infernix; QwFNfer/Ollama — по подтверждённым возможностям.

**Результат:** рекомендации учитывают текущие запуски, минимальный контекст и приоритет пользователя. Trial изолирован; оценка отличается от измерения.

**Приёмка:** параллельные старты не резервируют один и тот же свободный бюджет; неизвестная память остаётся unknown; occupied ≠ incompatible; минимум контекста не снижается. Рассмотрены offload, pinned RAM, workspace и shared service. Проверенный профиль получает условия и не называется подходящим всегда.

**Откат:** оставить ручные запуски и прежнюю advisory оценку; отключить автоматические рекомендации. Документация: формулы/границы каждого estimator, причины ранжирования.

### P08 — Задания тестов, изоляция и доказательства [L]

**Задачи:** перевести существующие suites/optimizer на jobs, cancellation и leases; scoped progress; сохранять snapshots, provenance, raw evidence и outcome восстановления. Адаптировать существующий план trial вместо параллельной второй реализации.

**Результат:** подбор и тесты работают при нескольких серверах без смешения истории и без скрытого влияния на рабочие подключения.

**Приёмка:** успешный, failed, cancelled trial не меняет профили/recovery; late progress принадлежит своему job. Recall/continuity используют реальные token counts при поддержке; missing API помечается unavailable. Cold/warm и фоновые нагрузки различимы. Старые результаты читаются; сравнение нескольких конфигураций воспроизводимо.

**Откат:** пользоваться прежними suites через выбранный запуск, запретив конфликты ресурсов; сохранённые результаты остаются читаемыми. Документация: точные протоколы, формат результата и ограничения выводов.

### P09 — Универсальное ручное и полуавтоматическое подключение [M]

**Задачи:** ConnectionTarget, discovery ID, endpoint/auth checks; копирование полей и блока, экспорт данных; точки входа в нынешней API-справке. Разделить настройки сервера и факт подключения клиента.

**Результат:** готовую модель можно подключить вручную за несколько действий, без чтения логов и командной строки.

**Приёмка:** данные соответствуют выбранному живому запуску, router profile ID и Ollama tag; secret скрыт до явного раскрытия/копирования; остановленная цель не помечена ready. Проверяются streaming, HTTP/SSE ошибки, auth и cancel; обещания tools/vision/context показывают основание проверки.

**Откат:** оставить текущую API-справку и прямые endpoints. Документация: ручное подключение и различия сетевых окружений.

### P10 — Автоматические адаптеры harness [L]

**Задачи:** выбрать первый harness и поддерживаемую версию, исследовать official integration mechanisms; preview/backup/apply/verify/undo и operation journal. Вторым адаптером проверить повторное использование контрактов.

**Результат:** приоритетный сценарий «Подключить» для выбранных harness, fallback экспорт/копирование для остальных.

**Приёмка:** existing config/providers/comments сохраняются в пределах формата; повторное применение не дублирует запись; изменение файла между preview/apply обнаруживается. Ошибка частичного применения и undo после сторонней правки не затирают пользовательские изменения. Проверка из harness отличима от проверки только Aplot.

**Откат:** undo только собственных изменений по журналу; если есть конфликт, показать diff для восстановления. Документация: каждая интеграция, поддерживаемые версии и рецепт адаптера.

### P11 — Необязательный стабильный API gateway [L, отдельное решение]

**Задачи:** после D05 при необходимости добавить небольшой Rust HTTP server, persistent aliases, discovery, auth, streaming/cancellation/backpressure и точные ошибки target state. Прямые endpoints сохраняются.

**Результат:** harness может использовать постоянный адрес и имя при смене backend; работа gateway связана с одним экземпляром Aplot.

**Приёмка:** прямой и проксированный одинаковый запрос сопоставлены; измерена добавленная задержка; stop/rebind alias не пересылает активный поток другой модели. Проверены client disconnect, HTTP 200 SSE error, медленный клиент, неизвестные поля/методы, idle timeout и размеры запросов.

**Откат:** отключить gateway и предложить прямой ConnectionTarget без потери профилей. Документация: protocol matrix, aliases, limits, diagnostics. Этот этап можно пропустить; P12 от него не зависит.

### P12 — Завершение перехода, документация и выпуск [L]

**Задачи:** удалить использованный legacy facade только после миграции callers; закрыть dependency violations; сверить RU/EN; подготовить release artifacts, hashes, migration/rollback instructions. Провести end-to-end на изолированной копии установки, затем согласовать использование рабочей базы.

**Результат:** рабочий выпуск с текущим UI, пятью адаптерами, несколькими запусками, профилями, лабораторией и проверенными подключениями.

**Приёмка:** вся матрица раздела 12; параметры и публичные контракты документированы; новый engine/harness можно добавить по рецепту без массовых правок core/UI. Известные ограничения перечислены, прошлые измерения не выданы за новые. Полная реструктуризация считается законченной только после проверки сохранения данных и пользовательских сценариев.

**Откат:** сохранённый EXE + совместимый backup базы; инструкции учитывают config changes harness и необязательный gateway. Документация входит в release readiness, не остаётся хвостом после выпуска.

## 12. Матрица проверок

| Область | Обязательные сценарии |
| --- | --- |
| Данные | v1/raw/v2 import, migrations repeat/failure, existing settings/layout/history/keys, known-good snapshots, missing paths |
| Lifecycle | A+B, один/разные engines, repeated start, stop during loading, restart, crash, port conflict, поздние события |
| Shared service | router routes, Ollama load/unload, конфликты одного tag, несколько потребителей, внешний endpoint |
| Ресурсы | одновременные reservations, allocation failure, unknown estimates, shared GPU, released leases, restore failure |
| Benchmarks | old/new results, SSE errors, token-count unavailable, cancel in each phase, сопоставимые cold/warm условия |
| Harness | preview/apply/repeat/partial failure/undo/conflict, credentials, фактическая модель, разные сетевые среды |
| UI | текущая навигация/карточки/layout, RU/EN, темы, масштаб, keyboard, целевые действия/tray/singleton |
| Документация | паритет разделов/параметров, локальные ссылки, реальные symbols, recipes, implemented vs planned |
| Gateway, если включён | SSE fidelity, cancellation/backpressure, errors/auth, alias routing, latency, target shutdown |

Проверки выполняются на трёх уровнях: unit для правил, contract/integration с лёгкими fixture-процессами и mock HTTP, native end-to-end с реально доступными моделями. Несколько процессов доказываются маленькими моделями; тяжёлые Flash-Next проверяются отдельно под допустимый бюджет. Нехватка ресурсов для двух больших моделей — проверка честной admission, а не повод выдавать неработающий запуск за поддержанный.

Текущие команды, из `app/` (проверены по манифестам/CI, при подготовке этого плана заново не запускались):

```powershell
npm run build
npm test
npm run verify:source
python -m unittest discover -s tests -p "test_*.py"
cargo fmt --manifest-path src-tauri/Cargo.toml -- --check
cargo test --locked --manifest-path src-tauri/Cargo.toml
cargo check --locked --manifest-path src-tauri/Cargo.toml
```

Для выпусков: `npm run tauri:build` и проверка настоящего EXE/установщиков. Новые contract/migration/docs checks включить в CI, не подменяя native verification. На каждой небольшой правке запускаются относящиеся к ней проверки; полный gate — на завершении этапа/релизе. Прохождение прошлых тестов не является результатом будущего рефакторинга.

## 13. Порядок, приоритеты и совместная работа

Последовательность зависимостей:

```text
P00 → P01 → P02 → P03 → P04 → P05
                                  ↓
                                 P06 → P07 → P08
                                  ↓
                                 P09 → P10
                                         ↓ по решению D05
                                        P11 (необязательно)
P05 + P06 + P07 + P08 + P09 + P10 → P12
```

P09 можно выполнять после P05, если ConnectionTarget работает через временный artifact reference. Документация идёт внутри каждого этапа. Параллельность задач не предполагает изменения одних файлов несколькими исполнителями; делегирование обсуждается отдельно.

Проверяемые рубежи:

- **M1 — внутренний фундамент:** P00–P03. Текущий UI и одиночные сценарии работают, профили есть у всех движков.
- **M2 — несколько запусков:** P04–P05. Одно окно независимо управляет несколькими сервисами/моделями.
- **M3 — лаборатория:** P06–P08. Модели, ресурсы и измерения согласованы с новой моделью запуска.
- **M4 — удобное подключение:** P09–P10. Копирование API и первые автоматические адаптеры.
- **M5 — готовый выпуск:** P12; P11 включается только по отдельному решению.

Перед каждым этапом вместе фиксируем желаемое поведение и несколько примеров. Затем готовим маленькие завершённые изменения, показываем результат в текущем UI, проверяем данные/регрессии, обновляем оба языка документации и записываем итог. Размер и сроки уточняем после P00 и первого перехода; календарные обещания до аудита не даются.

Карточка рабочей задачи: ID этапа, пользовательский сценарий, вход/выход, затронутые контракты/файлы, migration/rollback, acceptance checks, документация RU/EN, evidence и ограничения. План обновляется после каждого согласованного решения, а не остаётся неподвижным текстом.
