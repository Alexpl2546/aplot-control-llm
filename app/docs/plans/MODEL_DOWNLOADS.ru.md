# Скачивание моделей в Aplot Control LLM

Дата: 2026-10-22. Статус: D0–D3 реализованы; D4 проходит Windows-приёмку, включая реальные single/split GGUF, полную загрузку 3,18 ГБ с source SHA-256, докачку и crash recovery. Реальный инференс Strata ещё не подтверждён из-за отсутствующих весов. Реализованная поддержка — llama.cpp и Strata: [план сокращения движков](ENGINE_SCOPE.ru.md), [журнал реализации](IMPLEMENTATION-COORDINATION.ru.md), [приёмка](IMPLEMENTATION-ACCEPTANCE.ru.md).

## Рекомендуемое решение

Добавить самостоятельный менеджер загрузок в Rust и общий интерфейс в библиотеке. Первым источником сделать Hugging Face для файлов GGUF. Целевые движки новой версии — только llama.cpp и Strata; интеграция Ollama Registry из плана исключена. Скачивание должно продолжаться при переходах между экранами и сворачивании в трей, поддерживать паузу и восстановление после перезапуска.

Первый релиз: вставить ссылку Hugging Face или `owner/repository`, выбрать вариант GGUF, увидеть полный состав и размер, скачать и получить модель в библиотеке. Поиск по всему Hub и рекомендации по оборудованию добавить следующим релизом.

Готовность скачивания, совместимость с движком и успешный запуск — три отдельных результата. Скачанный GGUF не обязательно поддерживается установленной сборкой llama.cpp или Strata. Для Strata дополнительно проверяется наличие подготовленной конфигурации и требуемых файлов.

Новая загрузка должна иметь собственное состояние вместо общего `busy`. `db::model_library_path()` зависит от найденного installation root и возвращает `models/llama.cpp`: нужен отдельный выбор доступной для записи папки, в том числе для обычной установки приложения. Одна физическая копия GGUF может использоваться обоими оставшимися движками, если совместимость подтверждена; каталог не должен требовать дублирования весов по движкам.

## Варианты реализации

| Вариант | Преимущества | Стоимость и ограничения | Решение |
| --- | --- | --- | --- |
| Rust + Hub HTTP API + скачивание файлов | Встраивается в Tauri, позволяет управлять очередью, диском и прогрессом; не требует Python | Нужно реализовать корректную докачку, редиректы и проверку целостности | Основной путь для GGUF |
| `huggingface_hub` / `hf` как отдельный процесс | Готовый клиент Hub, поддержка его механизмов передачи и snapshot-загрузок | Поставка и обновление runtime, управление процессом, дополнительный кэш и интеграция прогресса | Рассмотреть для будущих snapshot-сценариев после измерений |

Для первого релиза проверить реальную HTTP-загрузку и докачку как LFS-, так и Xet-backed файлов. Производительность нативного пути измерить на больших GGUF. Решение об отдельном ускоренном клиенте принимать по результатам, не включать его в обязательные зависимости заранее.

## Пользовательский сценарий

1. В библиотеке пользователь нажимает «Скачать модель».
2. Вставляет ссылку репозитория Hugging Face, страницы файла, resolve-ссылку или `owner/repository`.
3. Для Hugging Face приложение показывает варианты GGUF: квантование, суммарный размер, число частей, дополнительные файлы. Выбор одного шарда разворачивается в полный набор этой квантовки.
4. Пользователь видит издателя, источник, ссылку на лицензию, папку назначения и требуемое место. Репозиторий без понятного квантования остаётся доступным через ручной выбор файлов.
5. Запускает загрузку. Панель показывает переданные байты, скорость, оставшееся время при известном размере, текущий файл и этап проверки. Доступны пауза, продолжение, повтор и отмена.
6. После проверки и установки модель появляется в библиотеке. Действия: «Открыть в библиотеке», «Создать профиль», «Открыть папку». Для Strata без подготовленной конфигурации показывается отдельное действие настройки, а не готовность к запуску.

Не создавать профиль и не запускать инференс автоматически. Не обозначать оценку RAM/VRAM как гарантию запуска. Доступность скачивания не должна зависеть от установленного движка или текущего фильтра библиотеки.

## Объём первого релиза

- Публичные Hugging Face-репозитории: загрузка конкретного GGUF или полного набора split-GGUF одной квантовки.
- Выбор сопровождающего `mmproj` с явным подтверждением; не подбирать проектор только по похожему имени. При недостатке метаданных показывать неопределённость.
- Один активный набор файлов и очередь следующих задач. Файлы внутри набора сначала загружать последовательно.
- Прогресс, пауза, повтор, отмена, сохранение состояния и докачка после перезапуска.
- Папка назначения, проверка места на целевом томе, защита от перезаписи существующих моделей.
- Статус совместимости с llama.cpp и Strata, включая состояние «для Strata требуется подготовка».
- RU/EN, режим браузерной демонстрации, понятные ошибки сети и доступа.

Gated/private-репозитории, поиск по Hub, произвольные HTTPS-источники, Safetensors snapshot, конвертация и автоматическая подготовка Strata — последующие этапы. В первой версии при ограниченном доступе показывать причину и ссылку на страницу репозитория.

## Архитектура и контракты

Предлагаемые новые модули:

```text
src/features/modelDownloads/
  types.ts / downloadRules.ts    состояния и чистые правила
  service.ts / store.ts          IPC, события и состояние интерфейса
  DownloadModelDialog.tsx        выбор источника и состава
  DownloadsPanel.tsx             очередь и управление

src-tauri/src/downloads/
  mod.rs / commands.rs           граница IPC
  manager.rs / repository.rs     жизненный цикл и сохранение
  transfer.rs / install.rs       передача, проверка и установка
  providers/huggingface.rs       разрешение репозитория и состава
```

Это ориентир разделения ответственности; точные имена согласовать с актуальной структурой при реализации. Не переносить загрузки в `control.ts` или менеджер бенчмарков.

Последовательность: интерфейс → подготовка плана → менеджер загрузок → адаптер источника → проверка файлов → установка → обновление существующей библиотеки.

Предлагаемые команды IPC:

- `resolve_model_download(source)` — получить варианты файлов и сведения об источнике.
- `prepare_model_download(selection, destination)` — зафиксировать revision, список файлов, место и конфликты; вернуть `planId`.
- `start_model_download(planId)` — перепроверить диск и конфликты, сохранить задачу, вернуть `downloadId` без ожидания завершения передачи.
- `list_model_downloads()` / `get_model_download(id)` — авторитетный снимок состояния.
- `pause_model_download(id)`, `resume_model_download(id)`, `cancel_model_download(id)` — управление.
- `remove_model_download_partial(id)` — отдельно удалить только принадлежащие задаче временные файлы.

Событие `download://updated`: `downloadId`, `sequence`, состояние, переданные/ожидаемые байты, скорость, текущий файл и структурированная ошибка. Ограничить частоту примерно до 4 событий/с и всегда отправлять смену этапа. При подключении интерфейса подписываться на события и получать снимок; `sequence` позволяет игнорировать запоздавшие данные. События не заменяют сохранённое состояние.

Состояния: `queued → resolving → downloading → verifying → installing → completed`. Дополнительно: `pausing`, `paused`, `retry_wait`, `failed`, `cancelled`, `interrupted`. Пауза подтверждается после остановки записи и сохранения контрольной точки. После аварийного выхода активные задачи становятся `interrupted`; пользователь получает действие продолжения. При штатном выходе задачи сохраняются как приостановленные; сворачивание в трей передачу сохраняет.

Сетевые ошибки повторять с ограниченным backoff; учитывать `Retry-After`. Ошибки авторизации, недостатка места и несовпадения хеша требуют отдельного действия. Для больших файлов разделить таймаут соединения и простоя передачи вместо фиксированного ограничения общей длительности загрузки.

## Хранение и целостность

Добавить отдельную транзакционную миграцию SQLite с таблицами `model_downloads`, `model_download_files`, `model_installations` и, на этапе авторизации, `download_source_secrets`. Не привязывать источник к конкретному профилю и не хранить его только в пересоздаваемом индексе артефактов.

Хранить: источник, repo ID, immutable commit SHA для Hub, путь файла в репозитории, размер, тип/значение проверенного digest при наличии, ETag/validator, состояние, пути назначения и временных файлов, контрольную точку, даты и ошибку. В `model_installations` сохранять происхождение, состав и результат проверки. Идентификация существующего артефакта по метаданным файловой системы не является проверкой содержимого.

Для файлов Hugging Face:

1. Разрешить branch/tag в commit SHA до начала передачи и сохранить его для всех частей набора.
2. Создать изолированный staging-каталог на том же томе, что и итоговая папка, например `<destination>/.aplot-staging/<downloadId>/`. Исключить его из всех сканеров моделей и артефактов; финальные расширения внутри него не должны становиться запускаемыми моделями.
3. Писать поток в файл `.part`; не загружать модель целиком в RAM. Периодически сохранять контрольную точку после сброса буфера. При восстановлении сверять запись БД с фактическим размером файла.
4. Докачивать через Range только при подтверждённой идентичности удалённого файла. Проверять `206` и `Content-Range`; при `200` начинать файл заново, при `416` сверять длину и целостность. Не дописывать новую версию в старую.
5. При истечении CDN URL заново разрешать адрес по сохранённым repo/revision/path. Не сохранять временный подписанный URL как постоянный источник.
6. Проверить размер и контрольную сумму, если источник предоставляет digest с известным алгоритмом. Не считать произвольный ETag или Xet-идентификатор SHA-256 файла. При отсутствии доверенного digest явно записать ограниченный уровень проверки; локальный SHA-256 сам по себе не доказывает совпадение с оригиналом.
7. Проверить структуру GGUF, комплектность шардов и роли файлов. При возобновлении безопаснее перечитать частичный файл для хеша, чем сохранять внутреннее состояние алгоритма между версиями приложения.
8. Опубликовать весь новый набор переименованием staging-папки в уникальную итоговую папку на том же томе, затем обновить индекс. Состояние `installing` и маркер установки должны позволять завершить регистрацию после сбоя между файловой операцией и транзакцией БД.

При уже существующей модели переиспользовать её только при достаточном подтверждении идентичности. Иначе предлагать отдельную папку; не перезаписывать файлы работающих моделей и профилей. Проверка свободного места учитывает оставшиеся байты всех задач на этом томе, уже существующие `.part` и резерв; ошибка записи также обрабатывается во время передачи. По умолчанию не создавать вторую полную копию набора.

Отмена останавливает задачу и сохраняет частичные данные до отдельного удаления. Удаление ограничено staging-каталогом конкретной задачи и не затрагивает существующие модели. Обслуживание компонентов должно учитывать активные загрузки.

## Подготовка модели для Strata

Текущая интеграция Strata использует подготовленные конфигурации `strata-*.json`. Успешное скачивание GGUF само по себе не создаёт конфигурацию, не устанавливает токенизатор и не подтверждает поддержку архитектуры.

В первом релизе скачивания сохранять общий GGUF и показывать отдельно готовность файлов, совместимость и готовность конфигурации. Если совместимость неизвестна, не предлагать запуск с уверенным статусом «поддерживается». Уже подготовленные конфигурации Strata должны продолжать обнаруживаться и запускаться.

Следующим этапом можно добавить мастер подготовки Strata: определить совместимый набор, выбрать токенизатор и необходимые сопутствующие файлы, создать конфигурацию через проверенный механизм установленной версии Strata и выполнить явную проверку готовности. До реализации этого этапа действие «Скачать» не обещает полную установку модели для Strata.

## Доступ к Hugging Face и безопасность путей

Для следующего этапа авторизации использовать read/fine-grained токен в DPAPI-хранилище, передавать в Rust по отдельной команде. Не возвращать токен в снимках задач, не помещать его в URL, журналы, настройки для экспорта или CLI-аргументы.

Разрешение доступа к gated-моделям пользователь выполняет на сайте Hugging Face. Приложение показывает «Открыть страницу доступа» и повторяет проверку после предоставления доступа.

Проверять HTTPS и каждый редирект; не пересылать исходный HF Authorization на произвольный CDN-хост. Принимать имена файлов только как относительные пути внутри staging: блокировать `..`, абсолютные и UNC-пути, Windows device names, alternate data streams и выход через ссылки/reparse points. Это требуется и для метаданных доверенного провайдера. Скачивание весов не запускает код репозитория.

## План внедрения и критерии готовности

Оценки ниже — рабочие дни одного разработчика, предварительные, с обычным ревью и без ожидания ручного доступа к закрытым репозиториям.

| Этап | Работы | Критерий готовности | Оценка |
| --- | --- | --- | --- |
| D0. Проверка протоколов | Spike HF resolve/redirect/Range на LFS и Xet; выбор папки и правила staging | Подтверждена докачка; зафиксированы контракты и граница подготовки Strata | 1–2 дня |
| D1. Ядро загрузок | Миграция, менеджер, очередь, потоковая запись, pause/resume, восстановление, shutdown | Искусственный обрыв и перезапуск продолжают файл без повреждения; UI не блокируется | 3–4 дня |
| D2. Hugging Face GGUF | Разбор ссылок, revision, варианты, шарды, проверка и установка | Одиночный и составной GGUF попадают в библиотеку только целиком; сбой установки восстанавливается | 2–3 дня |
| D3. Интерфейс библиотеки | Диалог, панель, независимый store, локализация, статусы llama.cpp/Strata, demo | Загрузка переживает переходы между экранами; готовность Strata показана отдельно | 1–2 дня |
| D4. Приёмка Windows | Ошибки диска/сети, конфликты, реальные модели, installer/portable/tray | Пройдены сценарии ниже; существующие импорт, профили и запуск работают | 2–3 дня |
| D5. Развитие после первого релиза | Поиск Hub с пагинацией и кэшем, token/gated, фильтры, ориентировочная оценка памяти | Поиск и доступ проверяются отдельно от факта совместимости | 3–5 дней |

Первый релиз скачивания D0–D4: ориентировочно **9–14 рабочих дней**, без отдельного этапа удаления старых движков и без автоматической подготовки Strata. После D0 уточнить объём D1/D2 по результатам Xet/Range и Windows-путей. При реализации маленькими PR сначала D0 и ядро, затем вертикальный сценарий одного GGUF, затем шарды и приёмка. Пользовательский релиз должен включать восстановление и целостность. Последовательность общей новой версии: сокращение движков → приёмка llama.cpp/Strata → подключение менеджера загрузок.

Обязательные проверки:

- HTTP-стенд: `206`, сервер игнорирует Range, неверный Content-Range, `416`, изменившийся validator, обрыв, timeout, редирект, `429`/`Retry-After`, несовпадение digest.
- Восстановление: закрытие приложения, аварийное завершение, несовпадение checkpoint и `.part`, сбой до/после переименования и до записи установки в БД.
- Файловая система: недостаток места, недоступный диск, кириллица/пробелы/длинные пути, конфликты имён, ссылки и traversal, повторная задача на тот же target.
- Состав модели: полный и неполный split-GGUF, проектор без основной модели, отсутствие автоматической публикации staging, успешный rescan после установки.
- Движки: один общий GGUF не дублируется для llama.cpp и Strata; отсутствие конфигурации Strata не маскируется успешным скачиванием; неподдерживаемая архитектура не получает разрешение запуска.
- Интерфейс: смена экрана, восстановление подписок, запоздалые события, RU/EN, управление клавиатурой, браузерная демонстрация.
- Реальная Windows-проверка на небольшом GGUF, большой модели и split-наборе, включая выход через меню и сворачивание в трей. Производительность фиксировать отдельно от unit-тестов.

При реализации выполнять относящиеся к изменению проверки frontend/Rust и действующие проверки границ модулей. Полный набор проверок приложения выполнить перед релизом; реальное скачивание не включать в обязательные сетевые unit-тесты.
