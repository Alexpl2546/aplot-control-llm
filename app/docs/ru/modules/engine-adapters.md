# Адаптеры запуска движков

## Назначение и исходники

[engine_adapters.rs](../../../src-tauri/src/engine_adapters.rs) подготавливает запуск одного из двух локальных движков: `llama_cpp` или `strata`. [runs.rs](../../../src-tauri/src/runs.rs) управляет временем жизни запуска, а [process.rs](../../../src-tauri/src/process.rs) создаёт и останавливает дочерний процесс. Общий тип `RunRequest` не делает параметры движков взаимозаменяемыми.

Адаптер — внутренний типизированный dispatcher, не система динамических плагинов. Разрешённые engine ID проверяются при разборе запроса; неизвестный или legacy ID завершается понятной ошибкой и не заменяется `llama_cpp`.

## Общие проверки и снимки

Подготовка отвергает пустые идентификаторы, неизвестный движок и router вне llama.cpp. Для процесса заявленный endpoint должен соответствовать последнему действующему `--port`; поддерживается `--flag=value`. Проверяются модель, бинарник и необходимые настройки до создания процесса.

Менеджер хранит запрос и подготовленную команду для restart. Редактирование UI не меняет уже работающий процесс. Это не снимок содержимого внешних файлов: бинарник, веса, Strata JSON и router preset остаются ссылками на файловую систему. Их замена вне приложения может повлиять на следующий запуск.

Каждый runtime владеет отдельным Windows Job с завершением потомков при закрытии, включая нативные дочерние процессы Python сервера Strata. Если назначение в job не удалось, запуск откатывается. Перед spawn проверяется доступность порта; автоматический выбор также учитывает резервирования других запусков. Wildcard bind остаётся в аргументах движка, а запросы локального API используют соответствующий loopback-адрес.

`prepare_run` не запускает модель. Планировщик ресурсов — отдельная read-only команда `plan_run_resources`; он возвращает рекомендацию и неизвестные значения, не записывает router preset и не резервирует память.

## llama.cpp и router

llama.cpp запускается через [StartServerRequest](../../../src-tauri/src/process.rs), который содержит исполняемый файл, аргументы, endpoint и настройки процесса. Single mode проверяет основную генеративную модель. Router mode использует preset; API ID берётся из профиля и определяется без изменения сохранённых имён.

Справочник frontend-аргументов находится в [parameters.ts](../../../src/lib/parameters.ts), построение команды — в [cli.ts](../../../src/lib/cli.ts). Порт в endpoint должен совпадать с итоговым `--port`. Router preset запуска подготавливается перед стартом и принадлежит этому run.

## Strata

[strata.rs](../../../src-tauri/src/strata.rs) принимает корень установки, выбранный `strata-*.json`, host, port и API key. Проверяются Python-окружение, layout Strata, исполняемый файл, tokenizer и пути из конфигурации. Для bind вне loopback нужен API key.

Запуск выполняется через `.venv/Scripts/python.exe -m serve.server --engine strata --config … --host … --port …` из корня Strata. Подготовленная конфигурация остаётся отдельной от скачивания GGUF: скачанный файл сам по себе не создаёт tokenizer или `strata-*.json` и не подтверждает совместимость. См. [загрузки моделей](models.md#hugging-face-downloads).

Метаданные запуска берутся из той же проверенной конфигурации, что и команда: пути нативных весов разрешаются против `cwd` конфигурации, пути tokenizer — против корня процесса Python. Отсутствующий рабочий каталог и нестроковые аргументы отвергаются до запуска.

## Сохранённые legacy-профили

Профили и экспорт сохраняют исходные поля и неизвестные engine ID для восстановления или ручной обработки. Запуск принимает только `llama_cpp` и `strata`; legacy ID явно отклоняется и не получает параметры другого движка. Движок меняется только после явного выбора пользователя и проверки его настроек.

Перезапуск использует снимок текущего запуска, а не свежие глобальные настройки. Router presets и JSON-конфигурации Strata остаются внешними файлами; их содержимое здесь не замораживается.
