# Управление запусками

## Назначение и исходники

[runs.rs](../../../src-tauri/src/runs.rs) управляет временем жизни запусков. [engine_adapters.rs](../../../src-tauri/src/engine_adapters.rs) проверяет настройки и формирует команду конкретного движка. [process.rs](../../../src-tauri/src/process.rs) создаёт и завершает дочерний процесс. [runtime.rs](../../../src-tauri/src/runtime.rs) нормализует наблюдаемые метрики. Эти обязанности разделены: изменение CLI движка не требует изменения логики переключения запусков.

Один экземпляр приложения содержит `RunManager`. Отдельный запуск обозначается `runId`; повторное создание процесса увеличивает `generation`. Сочетание этих значений отличает новую работу от задержавшихся логов старого процесса. Совпадение модели или профиля не означает совпадение запуска.

## Контракты

`RunRequest` содержит `runId`, `name`, `engine`, `mode`, `modelId`, `contextTokens`, `autoPort`, `launch`. Последнее поле разбирает адаптер движка. Полный запрос хранится в памяти; публичный `RunInfo` не содержит `launch` и API-ключа.

| Поле `RunInfo` | Смысл |
| --- | --- |
| `runId`, `generation` | Логическая цель действия и её поколение |
| `engine`, `mode` | Движок и single/router |
| `endpoint`, `modelId`, `contextTokens` | Параметры подготовленного запуска; реальный API model ID дополнительно проверяется discovery |
| `state` | starting/loading/ready/busy/stopping/stopped/crashed |
| `pid`, `startedAt` | Дочерний процесс и время старта |
| `managed` | Принадлежит ли запуску процесс приложения; доступность API проверяется отдельно |
| `lastError` | Последняя ошибка процесса/наблюдения |

## Команды и действия

| Команда | Аргументы | Поведение |
| --- | --- | --- |
| `prepare_run` | `{request}` | Проверяет модель/настройки, возвращает описание, не запускает процесс |
| `start_run` | `{request}` | Создаёт или запускает слот; одинаковый активный запрос возвращает прежний процесс |
| `list_runs` | — | Возвращает известные запуски и обнаруживает завершившиеся дочерние процессы |
| `stop_run` | `{runId}` | Останавливает только указанную цель; повторная остановка безопасна |
| `restart_run` | `{runId}` | Перезапускает прежний неизменяемый запрос |
| `stop_all_runs` | — | Завершает owned-запуски и owned-службы, собирает ошибки |
| `run_runtime` | `{runId}` | Собирает метрики именно этой цели; устаревшее поколение отвергается |
| `run_connection` | `{runId}` | Запрашивает `/v1/models`, возвращает проверенный ConnectionTarget |

Редактирование настроек не изменяет уже запущенный процесс. Для применения черновика UI выполняет stop → prepare/start с новым snapshot. Сам `restart_run` не читает текущие глобальные настройки.

## Автоматический выбор порта

`autoPort` — необязательный флаг; для прямых IPC-вызовов по умолчанию `false`, поэтому строгий запрос сохраняет ошибку при конфликте. UI включает его для llama.cpp (single/router) и Strata. Порт профиля становится предпочтительным: менеджер проверяет его и затем следующие порты, не более 256 кандидатов до 65535. Проверка системного bind пропускает порт стороннего процесса; блокировка реестра исключает выбор одного порта двумя одновременными стартами приложения.

Выбранный порт подставляется в CLI, endpoint и snapshot запуска. `RunInfo.endpoint` содержит фактический адрес; обзор, параметры выбранного запуска, API Docs и бенчмарки используют этот адрес. Сохранённый профиль не переписывается. Повтор исходного запроса возвращает тот же активный процесс; перезапуск предпочитает уже назначенный порт. Предварительный `prepare_run` показывает предпочтительный адрес и не резервирует порт.

Проверка bind не передаёт сокет дочернему процессу: сторонняя программа может занять порт между проверкой и стартом движка. Такой сбой остаётся ошибкой запуска и освобождает резерв приложения.

## Блокировки и гонки

`runs` хранит `Arc<RunSlot>`. Общая блокировка реестра нужна только для получения слота. Длительное ожидание процесса выполняется под `RunSlot.operation`, а не под реестром. `RunSlot.data` защищает snapshot/RunInfo; `ProcessState` защищает дочерний процесс.

Реестр портов атомарно резервирует порт до создания процесса. Освобождение удаляет только записи текущего владельца. Консервативная проверка по номеру порта предотвращает наложение wildcard и loopback адресов. Ошибка старта освобождает резерв и сохраняет crashed-запись для диагностики.

Измерение получает эксклюзивную `activity` lease и lease своего слота. Начало/остановка/перезапуск во время него возвращают ошибку с просьбой отменить бенчмарк. Это предотвращает незаметное изменение конфигурации между измерениями. При завершении задания guard освобождается автоматически.

## Router runs

У разных router-запусков разные presets в `data/routers/run-…/router-presets.ini`. `owner.json` проверяет принадлежность каталога; имя вычисляется из runId и не содержит пользовательского пути. Запись preset активного запуска отклоняется. Старые IPC-вызовы без runId сохраняют legacy-путь.

Frontend [router.ts](../../../src/lib/router.ts) одинаково формирует API ID для preset, запроса запуска, панели подключения и бенчмарков. Уникальное имя профиля остаётся API ID. Для одинаковых имён без учёта регистра используется `имя--encoded-profile-id`; дополнительный числовой суффикс разрешает совпадение с явно названным маршрутом. Имена профилей и их сохранённые ID не меняются. Порядок профилей не влияет на результат. Список маршрутов работающего сервера фиксируется при запуске: изменение, добавление и удаление профилей применяется после перезапуска. Для подключения клиента копируйте фактический ID из API Docs.

## События и завершение

`run://log` передаёт `{runId,generation,line}`. `run://state` передаёт `{runId,generation,state}`. UI хранит логи и историю отдельно, отбрасывает старые поколения. Наследуемые `llama://…` остаются для старого фасада и служебных сообщений.

Штатный Quit сначала отменяет задания и записывает их исход, затем останавливает owned-запуски. Закрытие в tray сохраняет процессы. Persistent daemon и восстановление процессов после аварии приложения не реализованы.

## Проверка и границы

Ignored-тест `real_multi_run_supervisor_smoke` запускается явно с `APLOT_SMOKE_BINARY` и `APLOT_SMOKE_MODEL`. Он запускает два CPU-сервера с одним предпочтительным портом и проверяет его автоматическое разделение, проверяет ответы обоих, дубли старта, конфликт порта, stop/restart/crash одного при работающем втором и общий shutdown. Отчёт задаётся `APLOT_SMOKE_REPORT`.

Проверка CPU процесса не доказывает совместимость каждого сочетания модели и GPU. Метрики GPU/RAM остаются общесистемными. Доступность памяти оценивается отдельным планировщиком; изоляция процессов сама по себе не обещает, что несколько больших моделей поместятся.
