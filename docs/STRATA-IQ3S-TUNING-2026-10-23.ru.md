# Strata IQ3_S: подготовка модели и подбор настроек, 23.10.2026

**Статус: полнооконные проверки 128K и 200K пройдены; оба профиля сохранены; EXE собран.** Для каждого контекста завершены три окна с результатом 160/160 проверок (100%); итоговые конфигурации прошли отдельные smoke-прогоны. Активирован профиль 128K на `127.0.0.1:8080`. Проверки выполнялись через native Strata API с теми же аргументами движка. Запуск сохранённых профилей из GUI Aplot этим отчётом не подтверждается; сам EXE проверен через read-only inventory.

## Почему скачанная модель выглядела неподдерживаемой

В приложении действительно находилась полностью скачанная модель: два GGUF-файла IQ3_S из репозитория [ISTA-DASLab/Qwen3.8-Flash-Next-GSQ-RCO-GGUF](https://huggingface.co/ISTA-DASLab/Qwen3.8-Flash-Next-GSQ-RCO-GGUF), а не маленькая тестовая модель. Предыдущая проверка поиска Hugging Face читала только метаданные и не скачивала эти веса.

На момент диагностики был выбран managed-компонент `project/components/strata/0.1.47`. В нём отсутствовала необходимая подготовка этой модели: pack, tokenizer, MTP и действующая `strata-*.json` конфигурация. Размещение GGUF внутри папки с именем `strata` не создаёт эти компоненты.

Обнаружение Strata требует действующей конфигурации, исполняемого файла и tokenizer; пути её входных файлов проверяются отдельно. Без найденной конфигурации библиотека не получает готовый источник Strata. Архитектура скачанной модели — `qwen4exp`; она также исключена из списка запуска llama.cpp в текущей интеграции приложения. Поэтому скачанные веса были видны, но готового движка у записи не было. Исправлять это простым присвоением совместимости всем GGUF нельзя.

## Обновление Strata и исправления приложения

Первоначальная подготовка и измерения выполнены в managed-компоненте `project/components/strata/0.1.48`: [Strata v0.2.3](https://github.com/Niko1221/Strata/releases/tag/v0.2.3), движок `0.1.48`, source commit `5c8dd322528cc84f68f461ad54a506b9da8fa8d4`. Этот commit совпадает с назначением официального аннотированного тега v0.2.3. URL, размеры и SHA-256 пяти закреплённых Windows-архивов CUDA/HIP сверены с метаданными GitHub. После измерений используемый код подготовки обновлён до source 0.2.3.1; бинарный движок остался тем же. Повторная проверка описана ниже.

Каталог моделей приложения читает таблицы установленного Strata, включая семейство, квантование и необходимые файлы. Поиск GGUF на Hugging Face для llama.cpp остаётся отдельным путём; формат GGUF сам по себе не подтверждает поддержку конкретной архитектуры установленной сборкой.

Для Python-среды, созданной через uv без pip, wrapper запускает встроенный `python -m ensurepip --upgrade` только при реальном `--setup`, если модуль pip отсутствует. Вызовы help и чтение каталога пакеты не устанавливают. Wrapper сохраняет выбранные каталоги данных на месте и не выполняет автоматическое перемещение старых установок. Отмена владеет только запущенным деревом процессов подготовки.

Для скачанного `qwen4exp` без подготовленной конфигурации карточка теперь показывает **«Нужна подготовка Strata»** и действие **«Подготовить для Strata»**, открывающее каталог Strata. Такая запись видна в фильтре Strata, но готовый источник движка ей не присваивается. После обнаружения проверенной конфигурации показывается обычное действие настройки модели.

Сведения о лицензиях Strata и Python-пакетов обновлены из установленного 0.1.48; остальные записи сохранены. Текст `integrations/strata/LICENSE` совпал с новым LICENSE. Лёгкие проверки wrapper, probe и сохранения профилей: 15 тестов прошли; они не запускают инференс.

## Условия измерений

ПК: **AMD Ryzen 7 9800X3D, NVIDIA RTX 5080 16 GB, RAM 64 GB**. Ограничение мощности GPU — **252 W**, без изменения этого лимита в ходе подбора. Измерения идут на движке 0.1.48; сборки и дополнительные нагрузочные CPU-тесты параллельно с GPU-прогонами не запускались.

Драйвер измерений — `project/app/artifacts/strata-tuning-2026-10-23/probe.py`; физическая папка артефактов — `local/artifacts/strata-tuning-2026-10-23`. Для каждого варианта сохранены исходная конфигурация, её SHA-256, рабочая копия запуска, запросы, ответы, журнал ресурсов и `results.json`.

Скорость измеряется через SSE: `promptTps` и `decodeTps` берутся из engine timings, TTFT — до первого видимого токена ответа. Вход считается API `/v1/chat/completions/input_tokens` и сверяется с usage ответа. Используются свежие запросы, фиксированный seed 42, отключённое reasoning и 256 выходных токенов. В обычной серии вход около 4096 токенов, три повтора; два prefill-варианта имеют вход около 32768 токенов и два повтора. Сравнивать эти две группы как одинаковую нагрузку нельзя.

Guard останавливает только принадлежащее проверке дерево процессов, если доступно менее 5 GiB RAM, 4 GiB commit или 768 MiB VRAM. Минимумы ниже измерены за весь запуск, включая загрузку. Это свободные ресурсы, а не потребление одной модели.

## Полнооконные проверки 128K и 200K

Оба прогона завершены с `ok=true` и `suiteSummary.passed=true`. Native Strata API сообщил фактический `n_ctx` 131072 и 204800 соответственно. На каждую конфигурацию выполнены три последовательных окна протокола `context-stability-v1`, версия 2:

- три recall-проверки по 20 текущих записей: 60/60;
- три checkpoint-проверки по 20 записей: 60/60;
- две carryover-проверки по 20 записей, в окнах 2 и 3: 40/40.

| Контекст / источник | Окна | Recall | Checkpoint | Carryover | Всего |
|---|---:|---:|---:|---:|---:|
| [131072](../app/artifacts/strata-tuning-2026-10-23/context-131072-ram25/results.json) | 3/3 | 60/60 | 60/60 | 40/40 | **160/160 (100%)** |

Успех относится к этому ledger-протоколу проверки текущих записей, checkpoint и переноса состояния между окнами. Он не является общей гарантией точности любой задачи на длинном контексте.
