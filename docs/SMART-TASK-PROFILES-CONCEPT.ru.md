# Смысловые настройки задач и автоматические профили Aplot

Дата: 14 октября 2026. Статус: концепция для обсуждения и утверждения; интерфейс и рабочие профили по этому документу ещё не изменены.

Документ предназначен для владельца продукта, дизайнера и модели, которая будет создавать интерфейсные референсы. Актуальное оформление приложения описано отдельно в [CURRENT-UI-DESIGN.ru.md](CURRENT-UI-DESIGN.ru.md).

## 1. Идея продукта

Человек выбирает задачу и описывает желаемое поведение несколькими понятными регуляторами. Aplot предлагает подходящую установленную модель, параметры ответа и конфигурацию сервера, объясняет выбор и показывает, что потребуется для применения.

Пример: «Кодинг → задача на несколько файлов → небольшая свобода решений → подробное объяснение». Результат: рекомендуемая модель, достаточный контекст, подходящий режим рассуждения, ограниченная вариативность и бюджет ответа. Вместо необходимости самому разбираться в temperature, KV, MTP и RAM человек видит смысл и последствия своего выбора.

Рабочее название блока: **«Настроить под задачу»**. Пресет задачи — например, «Кодинг» — отличается от существующего профиля запуска, например, «Qwen3.6 35B · 32K · Strata». Пресет описывает намерение; профиль запуска хранит конкретную конфигурацию движка. Смысловые настройки связывают их.

### Основные правила

1. При движении ползунка сразу меняется предварительный план. Сервер начинает применять изменения после явного действия «Применить» или «Запустить».
2. Человек всегда видит выбранную модель, контекст и необходимость перезапуска.
3. Автовыбор модели можно отключить и закрепить конкретную модель. Параметры, заданные вручную, тоже можно закреплять.
4. Система использует доступные возможности конкретной пары «веса + движок + версия + режим». Номинальные способности семейства модели недостаточны.
5. Тесты, рекомендации автора и предположения отображаются с разным уровнем подтверждения.
6. Ползунки не обещают гарантированную правильность, скорость или качество дизайна.

## 2. Что важно учесть в нынешнем приложении

Aplot управляет локальными серверами llama.cpp, Strata, Ollama, QwFNfer и Infernix. В нём уже есть профили, выбор запуска, мониторинг, бенчмарки, оценка памяти, API и подключения. Основной путь предполагает, что другой клиент обращается к API сервера.

Сейчас наличие `temperature=0.8` в сохранённом универсальном профиле не доказывает, что каждый движок получает именно 0.8. llama.cpp умеет получать sampler defaults через параметры запуска; у Strata Aplot запускает отдельный `strata-*.json`, а внешний клиент может явно задавать температуру в запросе. У Infernix температура не записана в его текущих engine-specific настройках. Поэтому новый блок должен показывать **реальный способ применения**, а не только красивую запись в профиле.

Наши тесты от 14 октября измеряли скорость, 12 небольших JSON-задач и для части моделей заполненный контекст. Они не являются специализированным рейтингом программирования, дизайна, зрения или автономных агентов. Рекомендация «лучший кодер по тестам» пока была бы необоснованной.

Также уточняется прежний совет о низкой температуре для кода: **0.2 — разумная стартовая гипотеза для прямых точных ответов, но не универсальный оптимум для каждой модели и режима**. Для Qwen3.6 автор отдельно рекомендует 0.6 при точном кодинге с рассуждением. Перевод semantic intent в sampler должен учитывать такие различия. [Официальная карточка Qwen3.6](https://huggingface.co/Qwen/Qwen3.6-35B-A3B).

## 3. Рекомендуемая структура управления

В основном блоке — выбор задачи и четыре ползунка. Более редкие настройки раскрываются по ссылке «Дополнительно». Справа или ниже находится карточка результата.

| Элемент | Вопрос человека | Формат |
| --- | --- | --- |
| Задача | «Что я делаю?» | Карточки/чипы пресетов с поиском |
| Креативность | «Сколько свободы и необычных решений?» | Ползунок 0–100 |
| Объём задачи | «Сколько материала нужно держать в работе?» | Ступенчатый ползунок; режим «Авто» |
| Глубина решения | «Насколько обстоятельно разбирать задачу?» | Ползунок с пятью смысловыми остановками |
| Подробность ответа | «Насколько развёрнутый результат мне нужен?» | Ползунок с пятью остановками |
| Приоритет | «Быстро получить ответ или тщательнее выбрать решение?» | Переключатель «Быстро / Баланс / Тщательно» |
| Рекомендуемая модель | «На чём это будет работать?» | Автовыбор + закрепление + альтернативы |

Ползунки описывают независимые свойства. Большой объём задачи не означает длинный ответ. Высокая глубина не означает высокую креативность. Низкая креативность не доказывает правильность ответа.

## 4. Креативность

**Подпись:** «Свобода вариантов». **Остановки:** «Предсказуемо → Вариативно → Необычно». Число справа можно показывать как 35/100; temperature остаётся в раскрываемой технической сводке.

Поведение:

- Повышать температуру в разрешённом диапазоне конкретной модели и режима.
- Если модель поддерживает и её рецепт проверен, согласованно менять top_p/top_k/min_p. Не менять одновременно все фильтры произвольным образом.
- В задачах генерации идей разрешать небольшую поправку presence penalty; для кода, точного извлечения и перевода по умолчанию сохранять её нейтральной.
- Менять рекомендации по числу концепций и свободе интерпретации брифа в шаблоне задания, если клиент умеет применять этот шаблон.
- Не менять размер контекста, число GPU-слоёв, MTP или квант только потому, что человек увеличил креативность.

### Предлагаемый общий рецепт для прямого ответа

Числа ниже — проектные стартовые значения, которые ещё нужно проверять на каждой модели. У model-specific рецепта приоритет выше.

| Креативность | Temperature | Top_p | Смысл |
| ---: | ---: | ---: | --- |
| 0 | 0 | 1.0 | Жадный выбор, режим для воспроизводимых коротких проверок |
| 20 | 0.2 | 0.90 | Мало вариаций, небольшие изменения кода/данных |
| 50 | 0.6 | 0.95 | Несколько естественных вариантов |
| 80 | 0.9 | 0.97 | Генерация концепций, альтернативные направления |
| 100 | 1.1 | 1.0 | Экспериментальные идеи; выше вероятность отклонений |

Для этого общего рецепта top_k/min_p сохраняются по рецепту модели. Если проверенного рецепта нет, базовый вариант использует только temperature и top_p, без новых штрафов. Интерполяция допустима между остановками; temperature=0 — отдельный режим. Фиксированный seed улучшает воспроизводимость теста, но не гарантирует одинаковые ответы при другой сборке, железе или размещении экспертов.

### Пример исключения для Qwen3.6

В режиме точного кодинга с рассуждением стартовать от рецепта автора: temperature 0.6, top_p 0.95, top_k 20, min_p 0, presence penalty 0, repetition penalty 1.0. Небольшая позиция ползунка означает ограниченную свободу постановки и решения задачи; она не обязана буквально означать temperature 0.2. Подсказка: «0.6 — рецепт этой модели для кодинга с рассуждением». При отключённом рассуждении другой рецепт должен иметь собственную отметку проверки. [Источник](https://huggingface.co/Qwen/Qwen3.6-35B-A3B).

Ползунок обязан сохранять монотонный смысл внутри одного рецепта: больше креативности не должно незаметно приводить к меньшей вариативности. Смена рецепта или режима показывается в сводке изменений.

## 5. Объём задачи и контекст

**Подпись:** «Материал в работе». **Остановки:** «Небольшой фрагмент → Несколько файлов → Большой документ → Большой проект». Помимо ползунка есть «Авто» и ручной ввод токенов в подробностях.

| Остановка | Ориентировочная потребность | Целевой контекст |
| --- | --- | ---: |
| Фрагмент | Короткая задача, один небольшой текст | 8K |
| Несколько материалов | Диалог, несколько файлов, небольшой бриф | 16K |
| Рабочий набор | Большой бриф или несколько содержательных файлов | 32K |
| Большой документ | Документы/код с длинной историей | 64K |
| Большой проект | Максимальный доступный проверенный набор | 128K |

«Большой проект» не обещает загрузку всего репозитория. Контекст измеряется токенами, а их число зависит от модели, языка, кода, изображений и структуры API. 256K и больше следует показывать только при наличии совместимой конфигурации и достаточного подтверждения на данном железе.

### Как рассчитывается значение

Если Aplot или подключённый клиент видит материал, используется точный токенизатор/API выбранной модели:

`нужный контекст = системные инструкции + история + текущий материал + схемы инструментов + бюджет рассуждения/ответа + резерв`

Подбирается минимальная разрешённая ступень, которая вмещает эту сумму. Например, вход 21K + инструменты/инструкции 2K + выход 4K + резерв 2K помещается в 32K. Вход 29K + выход 8K уже требует следующей доступной ступени или уменьшения материала. Двойной учёт reasoning tokens не допускается: часть API включает их в общий лимит вывода.

Если приложение не получает сам текст, оно показывает «Запрошено 32K; достаточность материала не проверена». Число страниц или файлов служит подсказкой, а не точным пересчётом.

### Действия системы

1. Проверить лимит архитектуры, движка, текущего режима и проверенных запусков.
2. Рассчитать память KV и сопутствующие расходы, не предполагая одинаковое устройство KV у всех архитектур.
3. Сопоставить потребность с занятостью RAM/VRAM и Windows commit, включая другие запущенные серверы.
4. При необходимости предложить другую проверенную конфигурацию размещения экспертов или другую модель.
5. Если выбранная модель не вмещает задачу, показать причину и варианты: другая модель, сокращение материала, разбиение задачи. Не обрезать материал незаметно.

Рост контекста может уменьшить место под экспертов в VRAM и снизить скорость. Поэтому контекст и параметры памяти рассчитываются вместе. Для llama.cpp нужно различать общий KV-пул и контекст на запрос: 65536 при двух слотах не автоматически означает 64K на каждый запрос. Для Strata KV resident 32768 не равен максимальному контексту 32768: проверенные Flash Next-профили обслуживают 128K со стримингом KV.

У текущей Qwen3.6 подтверждены два последовательных окна 32K. Два окна обозначают проверку переноса информации между этапами, а не два одновременных запроса. Вариант 64K проходил только короткий тест и не должен получать отметку «Полный контекст проверен».

## 6. Глубина решения

**Подпись:** «Разбор перед ответом». **Остановки:** «Прямой ответ → Лёгкий разбор → Обычный → Подробный → Сложная задача».

Регулятор влияет на выбор reasoning-совместимой модели, режим рассуждения и поддерживаемый бюджет. При высокой глубине система может рекомендовать модель, которая медленнее начинает отвечать, но лучше проходит соответствующие задачи. Она не включает reasoning по одному признаку в названии модели.

Если адаптер умеет подтвердить reasoning_effort/budget, используются они. У Qwen отдельно проверяется применение шаблона enable_thinking. Если движок не умеет управлять глубиной, показывается «Глубина задаётся заданием в клиенте» либо параметр недоступен. Разные API имеют разные форматы; универсальный `reasoning_effort` не отправляется вслепую.

Подробный разбор занимает часть контекста и лимита вывода. Нельзя увеличивать reasoning budget, оставляя слишком маленький общий бюджет и обрезая финальный ответ. Интерфейс показывает ожидаемую дополнительную задержку как оценку, когда для этого есть измерения.

MTP не является рассуждением: это ускорение генерации предполагаемыми токенами. Ползунок глубины напрямую его не меняет. Пользователю показывается краткое объяснение результата и проверок; демонстрация внутреннего полного рассуждения не требуется.

## 7. Подробность ответа

**Подпись:** «Размер результата». **Остановки:** «Коротко → С объяснением → Обычно → Подробно → Полный материал».

Меняется рекомендуемый верхний лимит вывода и, при подключённом шаблоне задания, желаемая длина результата. Проектные лимиты для прямого текста: 512 / 1024 / 2048 / 4096 / 8192 токена. Это верхние пределы; модель не обязана заполнить их. Для кода и длинного рассуждения используются более высокие task-specific значения, например 4K–8K для результата с несколькими файлами.

Лимит вывода входит в контекстный бюджет. Перемещение этого ползунка может потребовать большего контекста; такое связанное изменение показывается. Уменьшение лимита не повышает ток/с, но может сократить общую длительность ответа. Если ответ завершился по лимиту, Aplot/клиент должен различать это и нормальное завершение.

## 8. Приоритет скорости и тщательности

Рекомендуется переключатель из трёх положений вместо ложной точной шкалы «качество 83%».

- **Быстро:** среди моделей, которые удовлетворяют ограничениям задачи, выше вес задержки первого ответа и полного времени ответа.
- **Баланс:** сначала отсечь неподходящие/нестабильные варианты, затем учитывать пригодность, контекст и скорость.
- **Тщательно:** выше вес результатов соответствующих задач и подтверждения формата; допускается больше времени на ответ.

Приоритет может изменить рекомендуемую модель, reasoning budget, проверенный профиль MTP и размещение памяти. Он не разрешает автоматически уменьшать нужный контекст или снимать ограничения стабильности. MTP выбирается по замерам конкретной пары модели и движка; больше draft tokens не обязательно быстрее.

Не следует автоматически включать route tail skip или экспериментальный W4A4 ради положения «Быстро»: они могут менять вычисления и ответы. Такие режимы допускаются только как отдельные явно выбранные варианты с собственным результатом проверки. Для NVFP4 на текущем ПК W4A4 почти не изменил prefill; обещать ускорение FP4-ползунком было бы ошибкой.

## 9. Дополнительные смысловые настройки

| Настройка | Предложение | Реальное влияние и ограничение |
| --- | --- | --- |
| Соблюдение брифа | «Свободная трактовка / В рамках брифа / Строго» | Шаблон задания, ограничения формата, проверка результата в клиенте. Не равно гарантии правильности |
| Формат результата | «Текст / Markdown / Код / JSON / По схеме» | response_format/grammar только при подтверждённой поддержке; иначе шаблон + валидация |
| Новизна идей | «Развивать направление / Искать альтернативы» | Число вариантов и task-specific presence penalty; раскрывать только для творческих задач |
| Повторяемость | «Каждый раз новые варианты / Повторяемый эксперимент» | Seed и фиксированный снимок настроек; не обещать битовую идентичность |
| Запас для других приложений | «Работаю только с моделью / Параллельно работаю / Беречь компьютер» | Проверенный запас RAM/VRAM/commit, профили размещения; без права расходовать всю память |
| Одновременная работа | «Один запрос / Несколько пользователей» | Число запросов/слотов и пересчёт контекста на слот. По умолчанию один; в дополнительных серверных настройках |
| Изображения | «Без изображений / Анализировать изображения» | Фильтр по фактически работающему vision backend/projector, затем свой бюджет контекста |
| Инструменты | «Только ответ / Использовать инструменты» | Проверенная поддержка tool calling, схемы и template/parser. Не предоставляет права на действия само по себе |

Соблюдение брифа и креативность независимы. Пользователь может выбрать «Креативность 90 + строгое соблюдение брифа»: искать необычные композиции внутри заданных цветов, ограничений и структуры.

«Точность фактов» не стоит делать обычным ползунком: нужные источники, поиск, инструменты и проверка важнее маленькой температуры. Вместо него — опция «Проверять результат» с перечнем реально доступных проверок. Для кода это запуск проверок в клиенте, для JSON — схема, для документов — соответствие источнику. Aplot не изображает такие проверки как выполненные, если их выполняет только внешний инструмент.

## 10. Пресеты задач

Значения — предложения для начального поведения. T означает общий прямой рецепт; модель/режим может получить обоснованную поправку. Контекст везде адаптируется к материалу и железу.

| Пресет | Креативность | Общая стартовая T | Глубина | Ответ | Контекст по умолчанию | Особенности |
| --- | ---: | ---: | --- | --- | ---: | --- |
| Кодинг | 20 | 0.2 | Обычная | 4K | 32K | Минимально нужные изменения, соблюдать интерфейсы и стиль проекта |
| Быстрая правка кода | 10 | 0.1 | Прямой/лёгкий | 2K | 16K | Локальные исправления; низкая задержка важнее длинного разбора |
| Кодинг с инструментами | 20 | По модели | Подробная | Общий бюджет от 8K | 32K+ | Только проверенные tools/parser; контекст схем и результатов инструментов |
| Дизайн: идеи | 80 | 0.9 | Обычная | 2K–4K | 16K | Несколько различающихся концепций; сохранять ограничения брифа |
| Дизайн: доработка | 35 | 0.35–0.5 | Обычная | 4K | 32K | Сохранить дизайн-систему, подготовить изменения и спецификацию |
| Анализ и планирование | 25 | 0.3 | Подробная | 4K | 32K | Допущения, аргументы, альтернативы; reasoning-рецепт по модели |
| Документы и длинные материалы | 15 | 0.2 | Обычная | 4K | Авто, 32K–128K | Подтверждённое извлечение; источник и объём важнее максимального числа токенов |
| Данные / JSON | 0 | 0 | Прямой | 1K–2K | Авто, 8K–32K | Схема, строгая валидация, нейтральные штрафы |
| Перевод и редактура | 20 | 0.2 | Лёгкая | По объёму текста | Авто | Сохранение терминов и смысла, повторение терминов не штрафовать агрессивно |
| Тексты и истории | 75 | 0.85 | Обычная | 4K–8K | 32K | Варианты, стиль и связность; контекст предыдущих частей |
| Общение | 60 | 0.7 | Лёгкая | 1K–2K | 16K | Короткий отклик, естественный тон |
| Разбор изображения | 25 | По модели | Обычная | 2K | По бюджету изображения | Только реально проверенный vision-путь; пока кандидат, а не подтверждённый пресет |

### Кодинг: предложенное решение

Для общего direct-answer пресета выбрать 0.2 как стартовую точку в желаемом диапазоне 0–0.3. Температура 0 остаётся для строгих преобразований и повторяемого теста; 0.3 — для поиска нескольких реализаций. Проверить отдельно синтаксическую корректность, прохождение задач и соблюдение инструкций. Низкая температура не заменяет эти проверки.

Для Qwen3.6 с reasoning использовать отдельный coding-рецепт с T=0.6 по автору. Такой выбор объясняется рядом с моделью. Пользователь может закрепить 0.2 вручную; система отмечает, что это отклонение от выбранного рецепта и специализированный локальный результат для него отсутствует. [Источник](https://huggingface.co/Qwen/Qwen3.6-35B-A3B).

### Дизайн: предложенное решение

Разделить «Идеи» и «Доработку», поскольку они требуют разной свободы. Пресет «Идеи» предлагает, например, три разных направления и сохраняет обязательные цвета, размеры и содержание. Пресет «Доработка» требует конкретной спецификации и последовательности компонентов. Если пользователь хочет рассматривать скриншоты, нужна проверенная vision-модель; если он описывает интерфейс текстом, vision не обязательна.

Температура регулирует выбор текста в LLM. Она не управляет автоматически параметрами отдельного генератора изображений, Figma или итоговой эстетикой макета. Пресет должен передавать понятный бриф выбранному клиенту/инструменту.

## 11. Автоматический выбор модели

### Что является кандидатом

Кандидат — установленная комбинация конкретных весов, кванта, движка, версии, шаблона, режима reasoning и профиля памяти. Одна модель в llama.cpp и Ollama может иметь разные результаты и возможности. Суффикс MTP/Vision в названии не доказывает, что соответствующий путь сейчас работает.

Сначала отсечь кандидатов, у которых нет нужных файлов, формата, tools/vision, достаточного контекста или памяти, а также известна критическая несовместимость выбранного режима. Только после этого считать предпочтение.

### Использование результатов

Хранить отдельные оценки для кодинга, следования инструкциям, JSON, длинного контекста, vision, инструментов и скорости. Не превращать их в один глобальный «IQ модели». Для каждого результата нужны версия набора, число задач, дата, конкретный launch/request snapshot, режим, длина входа/выхода и оборудование.

Пример весов внутри уже подходящего набора, как проектная гипотеза:

| Приоритет | Результаты задач | Следование формату | Время полного ответа | Старт/переключение |
| --- | ---: | ---: | ---: | ---: |
| Быстро | 35% | 20% | 35% | 10% |
| Баланс | 50% | 20% | 20% | 10% |
| Тщательно | 65% | 20% | 10% | 5% |

Вес применяется только к сопоставимым измерениям. Пустой coding score не равен нулю и не превращается в 12/12 JSON. При отсутствии задачи-специфичных результатов использовать явно обозначенный предварительный порядок, уверенность и описание автора. Не показывать красивый процент уверенности без метода его расчёта.

Не переключать модель на каждое движение мыши. Во время редактирования меняется рекомендация; фактический выбор фиксируется после применения. До завершения текущего запроса активная модель не заменяется. Если другая модель лишь незначительно улучшает план, сохранение уже загруженной модели обычно полезнее, чем дорогое переключение. Порог следует выражать через измеренное время и пригодность, а не только ток/с.

### Что можно рекомендовать по нынешним данным

| Сценарий | Предварительный выбор | Основание | Чего ещё не знаем |
| --- | --- | --- | --- |
| Кодинг, рабочий набор до 32K | Qwen3.6 35B UD-Q4_K_XL / Strata | 76.4 ток/с, 11/12 JSON, tool probe прошёл, проверены 2 окна 32K; автор описывает coding-направленность | Нет локального coding-набора и замеров reasoning-кодинга |
| Строгие инструкции и длинный текст | Flash Next UD-IQ4_XS / Strata | 12/12, строго 12/12, 56.9 ток/с, заполненный 128K прошёл | 12 задач не доказывают общую или coding-победу |
| Строгие короткие преобразования | UD-IQ4_XS или RVN Qwen27 | У обоих 12/12 строгих ответов | RVN медленнее, полный 64K не проверен, MTP и кеш отключены |
| Быстрое общение | Уже загруженная подходящая модель; GPT-OSS / Ollama как кандидат | 219.6 ток/с, 10/12 коротких задач | Задержка запуска, реальные диалоги, поддержка нужного формата/режима |
| Дизайн по текстовому брифу | Qwen3.6 как начальный кандидат; альтернативы IQ4/Bonsai | Практичный баланс и доступные модели | Нет локального набора дизайна; эстетика не измерена |
| Разбор скриншота | Gemma E4B Vision как кандидат | Есть существующий профиль с vision-путём | Изображения в текущем цикле не проверены; автоматический выбор пока запрещён |
| Новый NVFP4 | Доступная альтернатива для ручного выбора | 22.1 ток/с, 10/12, 128K прошёл | Не показал преимущества по скорости на RTX 5080 / 64 ГиБ |

Qwen2.5 0.5B нельзя выбирать для серьёзного кодинга только из-за 670 ток/с: в текущем наборе лишь 3/12. GPT-OSS / llama.cpp имеет известные ошибки формата в части задач и 8/12; это ограничение именно установленной комбинации. Текущие показатели взяты из [локального отчёта](MODEL-REVIEW-2026-10-14.md). Информация автора Qwen служит отдельным основанием, не локальным тестом. [Карточка](https://huggingface.co/Qwen/Qwen3.6-35B-A3B).

### Как получить основание для «лучшей модели для кодинга»

Перед автоматическим утверждением такого статуса подготовить сопоставимый локальный набор: задачи Python/TypeScript/Rust, исправление ошибок, работа с несколькими файлами, соблюдение API, изменения frontend по брифу. Оценивать запускаемость и результат проверок, а не объяснение модели. Тесты выполнять в изолированных временных проектах с фиксированными условиями; отдельно сравнить прямой ответ, reasoning и инструменты. Дизайн оценивать отдельными брифами, соблюдением требований и человеческой оценкой референсов; предпочтения пользователя могут влиять на выбор после накопления отзывов.

Этот документ предлагает такие будущие проверки; при подготовке концепции они не запускались.

## 12. Перевод намерения в настройки

Порядок расчёта должен быть предсказуемым:

1. Прочитать исходный пресет, позиции ползунков и закреплённые параметры.
2. Определить обязательные требования: тип входа, tools, формат, входной/выходной бюджет, параллельность.
3. Выбрать подходящие модели и проверенные режимы; при закреплённой модели рассматривать только её.
4. Применить рецепт выбранной модели/режима к sampler и reasoning.
5. Рассчитать контекст и память, выбрать допустимую конфигурацию размещения.
6. Проверить совместимость MTP, кеша, KV, шаблона и запросных параметров.
7. Сформировать технический план, список изменений, причины, способ применения и статус подтверждения.

Результат состоит из двух частей:

- **Launch plan:** модель, движок, контекст, KV, размещение GPU/RAM, MTP, параллельность, порт; изменения могут потребовать перезапуска.
- **Request plan:** temperature, sampler, бюджет ответа, reasoning, формат и опциональный шаблон задания; применение зависит от сервера и клиента.

Объединённый «профиль задачи» хранит обе части. Рабочие проверенные профили остаются базой для создания производных вариантов. Смена смысловых ползунков не переписывает автоматически все сохранённые профили и базовый файл Strata.

### Закрепления и конфликты

Человек может закрепить модель, контекст, температуру или параметр в технических подробностях. При невозможности выполнить план система сообщает конкретный конфликт: «Закреплённые 32K не вмещают вход 29K и выход 8K». Она предлагает освободить контекст, сменить модель или сократить материал.

Если после ручного изменения пресет больше не совпадает, показывается «Кодинг · изменён», без сброса остальных позиций. «Вернуть пресет» возвращает смысловые значения; снятие закреплений — отдельное понятное действие.

## 13. Как параметры действительно доходят до модели

Это обязательная часть реализации.

| Путь | Применение | Что писать в интерфейсе |
| --- | --- | --- |
| Поддержанные defaults движка | Записать параметры в производный launch config; перезапустить при необходимости | «По умолчанию на сервере; клиент может переопределить» |
| Экспорт для внешнего клиента | Выдать корректные параметры запроса/шаблон для выбранного API | «Подготовлено для клиента; применение клиентом не подтверждено» |
| Интегрированный тестовый запрос Aplot | Сформировать и отправить запрос с request plan | «Применено к этому тестовому запросу» |
| Будущий локальный шлюз Aplot | Подставлять согласованные defaults в запросы через новый endpoint | «Применяется к запросам через этот адрес» |

Для первой версии достаточно реальных server defaults, экспортируемых request settings и прозрачного статуса. Полное управление произвольным внешним клиентом требует интеграции либо отдельного шлюза. Шлюз — отдельный будущий объём работ: streaming, инструменты, разные протоколы, ключи, ошибки и лимиты. Он не должен появляться в референсе как уже работающая функция.

По умолчанию явные параметры клиента имеют приоритет над defaults. Для будущего шлюза можно предусмотреть явно включаемый режим «Закрепить параметры профиля», в котором конфликт возвращается клиенту или разрешается по объявленной политике. Нельзя незаметно изменять параметры активного запроса.

### Состояния применения

- «Черновик»: ползунки изменены, сервер и клиент пока работают с прежними настройками.
- «Можно применить к следующему запросу»: request-only изменение и есть контролируемый запросный путь.
- «Нужен перезапуск»: изменились модель, контекст или launch defaults.
- «Нужна настройка клиента»: параметры подготовлены, но запросы идут напрямую к серверу.
- «Применено»: есть конкретный активный snapshot и подтверждённый путь параметров; scope указывается рядом.
- «Не помещается» / «Не поддерживается»: план невозможно применить с заданными закреплениями.

Существующий registry llama.cpp сейчас помечает sampler defaults как restartRequired. Новый режим request settings — отдельный слой; прежнюю отметку нельзя просто убрать, объявив все температуры «живыми».

## 14. Объяснение решения человеку

Карточка результата содержит:

1. Задачу и состояние: «Кодинг · изменён».
2. Модель и движок: «Qwen3.6 35B · Strata»; значок закрепления и ссылка на альтернативы.
3. Контекст: «32K на запрос»; для multitasking отдельно число запросов.
4. Поведение: «Небольшая свобода · обычный разбор · результат до 4K».
5. Память: диапазон оценки и запас; отдельно отметка измеренного близкого профиля.
6. Основание: «32K проверен; кодинг — предварительная рекомендация».
7. Применение: «Нужен перезапуск» или «Экспортировать параметры клиенту».
8. Краткий diff: «temperature 0.8 → 0.2; output limit → 4K; контекст без изменения» — только реальные изменения.

Ток/с из 4K теста показывать как «Измерено около 76 ток/с при входе ~4K», а не гарантированное значение для любой задачи. Не переносить его в режим рассуждения или контекст 128K без сопоставимого измерения. Если сведений недостаточно, показывать «Не измерено».

Объяснение «Почему эта модель?» должно быть коротким: «Вмещает 32K, прошла tool probe, быстро обрабатывает вход. Специализированный coding-тест ещё не проведён». Альтернативы показывают причины пригодности и ограничения, а не только место в рейтинге.

## 15. Встраивание в текущий интерфейс

Основное место — **«Параметры запуска»**. Внутри добавить переключение «Под задачу / Параметры движка». Это не новая глобальная навигация. Режим «Под задачу» становится понятной стартовой точкой; технический редактор остаётся доступен.

На «Главной» — компактная строка активного режима рядом с серверной карточкой: «Кодинг · 32K · Баланс» и действие «Настроить задачу». Не размещать четыре ползунка в каждой телеметрической плитке.

В библиотеке профилей показывать производные task-профили с пресетом и признаком изменения. Существующие имена API-маршрутов/моделей не менять ради нового красивого ярлыка. У каждого запуска свой snapshot задачи; переключение CH1/CH2 не должно переносить настройки между серверами.

При узком окне результат располагается под регуляторами. Видимые подписи и значения обязательны; цвет помогает, но не заменяет текст. Есть клавиатурное управление, Home/End, стрелки, смысловой aria-valuetext, ввод значения, кнопка возврата к пресету. Модель не переключается во время drag; preview обновляется после короткой задержки, например 150–250 мс.

## 16. Какие референсы нужны после утверждения

Сначала проработать один согласованный экран «Параметры запуска → Под задачу» и его состояния; дизайн-токены взять из отдельного описания текущего интерфейса.

1. Широкий тёмный экран 1920×1080, «Кодинг», четыре регулятора, справа результат.
2. Тот же экран в светлой теме с теми же ролями цветов.
3. «Дизайн: идеи», высокая креативность и строгое соблюдение брифа.
4. «Документы»: запрос 128K и предложение перейти с закреплённой Qwen3.6 32K на проверенный IQ4.
5. «Недостаточно памяти»: конкретный конфликт и возможные действия.
6. «Сервер работает»: request changes отдельно от изменений с перезапуском; виден текущий snapshot.
7. «Нужна настройка клиента»: export без ложной отметки «Применено».
8. Панель «Почему эта модель?» с двумя альтернативами и честными статусами подтверждения.
9. «Кодинг · изменён»: ручное закрепление температуры и отмена изменения.
10. Компактное окно около 1280×800: сохранённая навигация, результат ниже регуляторов.

Референсы показывают эти интерфейсные состояния, а не предполагают уже работающий автотюнинг. Не нужны декоративные «проценты интеллекта», радарные диаграммы качества без измерений или обещание полной памяти репозитория.

## 17. Предлагаемые этапы реализации

### Первая версия

Четыре ползунка, пресеты, ручное закрепление модели, предварительные рекомендации из существующих измерений, model-specific sampler recipes, производный launch/request snapshot, честное применение и экспорт параметров клиента. Контекст выбирать из допустимых проверенных конфигураций; неизвестные engine-managed расходы обозначать как неизвестные. Предварительный план работает без запуска нового бенчмарка при каждом движении.

### После проверки первой версии

Специализированные coding/tools/vision/design-наборы, импорт измерений в каталог пригодности, измеренный подбор размещения и контекста, пользовательские предпочтения и задачи. Отдельно решать необходимость шлюза для внешних клиентов. Новые эксперименты выполнять явным действием и сохранять результат отдельно от проверенного рабочего профиля.

### Критерии готовности

- Человек понимает по экрану, какая модель и контекст будут использованы.
- Видно отличие черновика от реально работающего запуска.
- Параметры доходят до модели заявленным путём; запрос клиента с другой температурой не скрывается.
- Нет объявления coding/design-победителя по JSON-набору.
- Известные ограничения RVN, Ornith и NVFP4 сохраняются при создании производных профилей.
- Объём задачи и лимит ответа учитываются совместно; контекст на слот показан правильно.
- Память не расходуется сверх допустимого плана; неизвестная оценка не изображается как зелёная гарантия.
- Можно восстановить исходный пресет/профиль и увидеть diff.
- Светлая/тёмная тема, клавиатура и узкое окно дают тот же понятный путь.

## 18. Рекомендованный вариант для утверждения

Утвердить четыре основных ползунка, переключатель приоритета и model-aware перевод настроек. Для общего прямого кодинга выбрать стартовую T=0.2; для Qwen3.6 с reasoning использовать её рецепт T=0.6 с пояснением. Предварительно предлагать Qwen3.6 для рабочего набора до 32K и IQ4 для строгих длинных материалов, не маркируя их победителями кодинга/дизайна до нужных тестов.

Первый дизайн делать внутри нынешней страницы «Параметры запуска», с карточкой результата и состояния применения. После утверждения этого принципа можно генерировать референсы по списку выше.
